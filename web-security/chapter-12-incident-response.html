COURSE OUTLINE / CHAPTER 12

DETECT, RESPOND, RECOVER

日誌、事件處理與完整防禦計畫

預防控制一定會有缺口。成熟防禦的差異，是能否快速看見真正異常、保留證據、停止權限、維持溝通、從可信備份恢復，並把每次事件轉成可驗證的改善。

90–120 分鐘8 個完整段落偵測、應變與復原授權環境限定

LEARNING OUTCOME

完成本章後，你能定義安全事件 Schema、選擇可行動告警、建立嚴重度與角色分工，執行保存證據、隔離、Secret／Session 撤銷、可信還原與復原驗證，並產出一份 30 天自家網站防禦計畫。

SAFE PRACTICE BOUNDARY

事件處理涉及真實資料、法律、隱私與營運決策。本章提供準備與協作框架，不授權你進入受影響系統之外的帳號或採取反擊；重大事件應依公司政策聯絡資安、法務、隱私與平台供應商。

01

LOG DECISIONS, NOT JUST ERRORS

Web Server Access Log 不足以還原登入、授權與商業決策

應用安全日誌要記錄身分建立與失敗、MFA、Session 發放與撤銷、授權允許／拒絕、管理操作、資料匯出、Secret 與設定變更、檔案處理、Webhook、限速、Egress 拒絕和部署。每個事件使用一致名稱、時間、環境、服務、版本、Actor、Action、Object、Outcome、Reason 與 Correlation ID。

日誌同時是敏感資產：不記密碼、完整 Session／Access Token、重設連結、Secret、信用卡或不必要個資；換行與控制字元正規化以防 Log Injection。集中傳送到限制權限的儲存，設定保留、完整性、時間同步、容量上限與失敗行為，確保記錄本身不會填滿磁碟拖垮應用。

ACTOR誰做的

使用者／服務雜湊 ID、角色、租戶、來源與裝置

ACTION做了什麼

事件名稱、Endpoint、Policy、版本與請求 ID

OBJECT影響什麼

物件類型與安全 ID，不記不必要內容

OUTCOME結果與原因

成功、拒絕、失敗、風險等級與 Reason Code

圖 1｜可關聯的安全事件 一致欄位讓跨登入、應用、雲端與部署資料能被搜尋與時間排序。

02

ALERT ON ACTIONABLE SIGNALS

不是每個錯誤都叫醒人，告警必須連到下一步

高價值偵測案例包括管理員登入異常、MFA 因素變更、成功登入後大量匯出、跨帳號授權拒絕、Secret 存取來源改變、CI Workflow 修改、Egress 連線被拒絕、檔案掃描失敗、Queue Age 超標和備份失敗。每條規則要有 Owner、Threshold、資料來源、抑制、嚴重度與 Runbook。

用正常基準、速率和多訊號關聯降低誤報，告警內容提供 Who／What／When／Where、影響範圍、證據連結和最安全的第一步；但不要把完整 Token 或敏感 Payload 放進通知工具。定期檢查規則是否從未觸發、總是誤報或沒有任何人處理，無主告警等於沒有偵測。

EVENTS一致資料

應用、身分、雲端、CI、Edge 與資料庫事件

DETECT基準與關聯

時間窗、速率、跨來源、成功後行為與資產價值

TRIAGE嚴重度與範圍

確認可信度、影響、持續性與資料敏感度

RUNBOOK明確下一步

Owner、時間、保存證據、隔離與升級路徑

圖 2｜告警必須能行動 有訊號不等於有偵測；最後必須有人能在時間限制內做出安全決策。

03

DECLARE AND COORDINATE

越早建立共同事件狀態，越少人各自做出衝突變更

事件嚴重度可依機密性、完整性、可用性、權限層級、影響使用者、法規與持續活動評估。區分 Event、Alert 與 Confirmed Incident，並允許隨新證據升降級。啟動後指定 Incident Commander、Technical Lead、Scribe、Communication、Business／System Owner，以及必要的法務與隱私窗口。

建立單一時間線與事實來源，記錄每個決策的時間、執行者、假設、命令或變更單、結果與回復方式。溝通分內部狀態、使用者通知、供應商與監管需求，內容只陳述已確認事實和下一次更新時間。預先準備 Out-of-band 聯絡方式，避免主要信箱或聊天平台受影響時失去協調。

COMMANDIncident Commander

設定目標、優先順序、嚴重度與決策節奏

TECHNICAL調查與處置

保存證據、確認範圍、隔離、修復與驗證

SCRIBE單一時間線

事實、決策、命令、變更、結果與待辦

COMMS分眾溝通

內部、使用者、供應商、法務、隱私與主管

圖 3｜事件角色不是職稱 小團隊可一人兼任多角，但決策、執行、紀錄與對外溝通責任仍要清楚。

04

PRESERVE BEFORE YOU CHANGE

急著重開機或清 Log，可能讓真正範圍永遠無法確認

先記錄系統時間、警報、受影響資產、帳號、IP、版本、部署、正在執行的程序、連線與相關日誌位置，依組織程序建立 Snapshot 或匯出唯讀副本。使用已知乾淨管理裝置與 Out-of-band 帳號，避免調查工具改變過多證據或把憑證送進受影響主機。

Chain of Custody、隱私與保存要求依組織與法域不同，重大事件要由合格團隊決定。對個人網站至少保留原始事件、雜湊、取得時間、取得者與存放位置；分析在副本進行。確認範圍從最早異常、第一個受影響身分、相同 Indicator、相同部署與相鄰資產展開，但不越過你有權管理的系統。

ORIGINAL原始系統與日誌

限制變更，記錄時間、狀態、版本與可疑活動

PRESERVESnapshot／匯出

唯讀、雜湊、取得者、時間與存放位置

ANALYZE在副本調查

建立 Indicator、主體、資產與時間關聯

TIMELINE共同事實

區分已知、未知、假設、決策與證據來源

圖 4｜先保存再修改 處置速度重要，但可逆、可追蹤的第一步能避免破壞範圍判斷與後續責任。

05

CONTAIN THE CAPABILITY

優先停止攻擊者的能力，同時避免把服務推進更大故障

隔離選項依情境包括停用帳號、撤銷 Session／Token、輪替 Secret、封鎖惡意部署、限制 Egress、把主機移出流量、暫停昂貴功能或切換唯讀。先處理能繼續擴張的高權限能力，再處理單一 Indicator；只封一個 IP 容易漏掉其他 Session 或憑證。

每項處置都評估對證據、使用者、資料一致性與復原的影響，記錄回復方式。Secret 輪替依 Consumer 順序使用雙版本過渡，確認新值生效後撤銷舊值；若簽章或加密金鑰受影響，還要分析既有資料與 Token 的信任。清除不是只刪檔案，而是修補入口、移除持久權限、重建受影響資產並驗證。

IDENTITY撤銷高權限

Session、Token、Key、MFA 因素、服務帳號與 CI 權限

NETWORK限制擴張

Egress、Route、管理入口、第三方 Trust 與流量切換

ASSET隔離受影響系統

移出負載、唯讀、Snapshot、停止可疑 Job

ROOT CAUSE修補並重建

安全配置、程式修正、乾淨 Image 與完整驗證

圖 5｜停止能力而不只封 Indicator 隔離應優先撤銷可重複使用的權限，再縮小網路與資產範圍。

06

RESTORE TRUST, NOT JUST DATA

備份成功訊息不等於能在事件中安全還原

備份策略依資料價值定義 RPO 與 RTO，採多份、不同媒介或帳號、至少一份離線或不可變，並分離刪除權限。備份包含資料、設定、IaC、必要金鑰保管與重建文件，但不要讓同一受害管理帳號能同時刪除正式和所有備份。定期自動驗證完整性，還要實際還原到隔離環境。

事件復原先確認備份時間點早於入侵且不含惡意變更，用乾淨 Image 與修補後配置重建，再還原資料；輪替受影響憑證，逐步接回依賴與流量。驗證不只看服務啟動：檢查資料一致性、授權、日誌、告警、效能、Queue、第三方對帳與使用者關鍵任務。

CLEAN BASE已知良好 Image

修補根因、固定版本、驗證來源與最小配置

BACKUP選擇可信時間點

離線／不可變、完整性、RPO／RTO 與惡意變更檢查

REBUILD重新建立資產

輪替憑證、還原資料、恢復日誌與監控

VALIDATE逐步接回流量

功能、授權、資料、效能、告警與業務對帳

圖 6｜恢復的是信任 若不知道備份是否乾淨、配置是否修補，快速還原可能只是把同一問題重新上線。

07

LEARN WITHOUT BLAME

事後檢討不是找一個人負責，而是修正讓錯誤擴大的系統

Post-incident Review 記錄影響、偵測方式、完整時間線、哪些控制有效、哪些訊號缺失、決策延遲、使用者與成本影響、根因和促成條件。區分 Trigger 與 Systemic Cause：某個設定錯誤可能是觸發點，但缺少審核、測試、最小權限、告警與回滾才讓影響擴大。

改善項目要有 Owner、優先級、截止日與可驗證完成條件，涵蓋 Prevent、Detect、Respond、Recover 四類；不要只新增文件或永久封鎖。完成後更新架構圖、資產表、威脅模型、Runbook、偵測規則、演練與教育，並在後續變更確認沒有退化。分享內容去識別化，保護使用者與調查敏感資訊。

PREVENT減少再次發生

安全預設、審核、最小權限、隔離與移除入口

DETECT更早看見

事件 Schema、基準、關聯、告警與擁有者

RESPOND更快停止

Runbook、角色、短效權限、撤銷與供應商協調

RECOVER可信恢復

乾淨 Image、還原演練、RPO／RTO 與驗證清單

圖 7｜把事件轉成防禦資產 每個重大發現至少落入一個可測試控制，而不只是『提醒大家小心』。

08

TURN THE COURSE INTO A SYSTEM

十二章的成果，最後要變成有順序、有擁有者的改善路線

把第一章資產圖與後續成果合併：HTTP 路徑、外露面、身分生命週期、授權矩陣、Injection Sink、瀏覽器基準、檔案流程、Outbound Inventory、交付鏈、可用性預算與事件 Runbook。以公開可達性、權限、資料價值、可偵測性與復原難度排序，不平均分配時間。

30 天計畫分四週：第一週關閉高風險入口與開啟 MFA／備份告警；第二週修正登入、授權與 Injection 等根因；第三週縮小雲端、Secret、Egress 與 Pipeline 權限；第四週完成告警、桌上演練與還原驗證。每項工作寫成果證據，例如測試通過、權限差異、演練時間或截圖，而不是只標『已改善』。

WEEK 1止血與可復原

關閉廢棄入口、管理員 MFA、備份告警與擁有者

WEEK 2應用根因修正

登入、授權、參數化、輸出、檔案與 API 測試

WEEK 3平台縮權

IAM、Secret、CI、Artifact、Egress、Patch 與漂移

WEEK 4偵測與演練

告警、Runbook、桌上推演、還原與改善證據

圖 8｜30 天防禦路線 先降低最壞風險，再修根因、收斂平台，最後用偵測與演練證明整套系統可運作。

FIELD ASSIGNMENT

用 75 分鐘完成迷你事件演練與 30 天計畫

採桌上推演，不在正式環境真正停用或輪替任何資源；若要實作變更，另依變更流程執行。

  1. 00–15

    選一個情境例如管理員 Token 外洩、未授權匯出、惡意部署或備份失敗，定義嚴重度與角色。

  2. 15–35

    走過事件時間線列偵測、保存證據、隔離、撤銷、溝通、清除、還原與驗證決策。

  3. 35–50

    檢查日誌與告警確認事件需要的欄位、資料來源、告警 Owner、Reason Code 和 Runbook。

  4. 50–75

    排 30 天改善依風險選 8–12 項工作，指定 Owner、期限、驗證證據與下一次演練日期。

CHECK YOUR MODEL

先回答，再展開。

只開 Web Server Access Log 足夠調查帳號事件嗎？

通常不足。還需要應用層身分、授權、Session、管理操作、物件與結果的結構化事件。

事件發生後是否應先立刻重開所有主機？

不一定。先評估保存證據、使用者影響與可逆性；重開可能破壞易失證據或隱藏範圍。

封鎖可疑 IP 就算完成隔離嗎？

不算。還要撤銷 Session、Token、Key、服務權限與惡意部署等可重複使用能力。

備份每天成功是否代表可復原？

不代表。需驗證完整性、權限隔離、乾淨時間點，並實際還原與測試關鍵任務。

Postmortem 最重要的產物是什麼？

有 Owner、期限和驗證條件的系統改善，涵蓋預防、偵測、回應與復原，而不是歸咎個人。

CHAPTER 12 / RECAP

完整防禦的終點，是可偵測、可停止、可恢復。

01

安全日誌記錄身分、動作、物件、結果與關聯 ID，同時排除密碼、Token、Secret 與不必要個資。

02

告警必須有擁有者、嚴重度、證據與 Runbook；事件啟動後建立角色與單一時間線。

03

先保存證據，再撤銷高權限能力、隔離資產、修補根因並從可信基準重建。

04

備份要實際還原，事件後把改善排進 30 天計畫並用測試與演練證明完成。
