COURSE OUTLINE / CHAPTER 05

AUTHORIZE EVERY REQUEST

權限控制與 IDOR

系統知道你是誰，不代表你能讀取任何物件。真正的授權必須在每一個 Endpoint、每一個動作、每一筆物件與每一個租戶邊界重新確認。

60–80 分鐘8 個完整段落物件層授權授權環境限定

LEARNING OUTCOME

完成本章後，你能分辨 Authentication 與 Authorization，辨認水平、垂直與多租戶越權，設計一致的伺服器端 Policy，並用兩個測試帳號建立正向與負向授權測試。

SAFE PRACTICE BOUNDARY

練習使用你自己的本機資料、測試帳號與假物件，禁止修改陌生網站的識別符或存取非授權資料。頁面只說明驗證方法與安全結果，不提供外部枚舉技巧。

01

IDENTITY IS NOT PERMISSION

先回答「你是誰」，再回答「你現在能做什麼」

Authentication 建立主體身分，例如匿名訪客、會員、客服或管理員；Authorization 則針對特定資源和動作做決策。登入成功只證明某個身分完成了驗證，沒有自動賦予讀取全部訂單、修改其他使用者資料或呼叫管理功能的權利。

一個完整授權問題至少包含主體、動作、物件與脈絡：誰要對哪一筆資料做什麼，是否屬於同一租戶，現在是否處於允許狀態，是否剛完成高強度驗證。把這些條件集中成 Policy，會比在每個 Controller 裡零散寫 if 更容易測試與稽核。

SUBJECT誰

使用者、服務帳號、角色與租戶

ACTION做什麼

讀取、建立、修改、刪除、匯出

OBJECT哪一筆

訂單、文件、帳號、設定或報表

POLICY允許或拒絕

伺服器端預設拒絕並記錄結果

圖 1｜四個授權輸入 物件 ID 不是權限；決策必須結合目前主體、動作與脈絡。

02

NAME THE FAILURE

越權不是一種畫面錯誤，而是伺服器做錯了決策

水平越權發生在同等角色間，例如會員 A 讀到會員 B 的資料；垂直越權則是低權限使用者取得客服或管理員功能。IDOR 是常見的物件層授權缺失：請求帶著 ID、UUID、Slug 或檔名，伺服器成功找到物件，卻沒有驗證目前主體是否有權操作。

隱藏按鈕、停用表單欄位或在前端檢查角色都只改善介面，不能成為安全邊界，因為使用者能直接送出請求。真正控制必須在伺服器接收每一個動作時執行，包括檢視、更新、刪除、匯出、批次操作和背景工作。

HORIZONTAL跨使用者

相同角色卻接觸另一個人的物件

VERTICAL跨角色

一般使用者取得管理或客服能力

OBJECT LEVEL缺少物件檢查

找到資料後沒有確認所有權或租戶

FUNCTION LEVEL缺少動作檢查

Endpoint 存在但沒有角色或能力限制

圖 2｜常見越權形狀 用具體主體、物件與動作描述失敗，才能寫出對應的負向測試。

03

CHECK ON THE SERVER

把資料範圍寫進查詢，比讀出後再判斷更可靠

安全的物件查詢不是先用全域 ID 找到資料，再看看 owner_id 是否相同；而是從目前主體允許的範圍開始查，例如 current_user.documents.where(id=...). 這讓「找不到」與「不在允許範圍」共同落入拒絕結果，也降低程式忘記檢查的機會。

所有資料來源都要一致套用：主要 API、GraphQL Resolver、批次匯出、WebSocket、背景任務、行動版舊 API 與管理工具。如果服務之間傳遞主體資訊，接收端仍需驗證 Token 與 Claims，並在本地做最終授權，不能只相信上游說已經檢查。

RISKY全域找物件

find(id) 後依賴每個呼叫點記得檢查

FAILURE遺漏一處

任何新 Endpoint 都可能繞過授權

PREFER主體範圍查詢

allowed_objects.where(id) 先縮小資料集合

RESULT預設拒絕

不在範圍就不回傳，不洩漏物件是否存在

圖 3｜從允許範圍開始查 把租戶和擁有者條件寫進資料存取層，可讓安全預設更難被略過。

04

MODEL THE POLICY

RBAC 管角色，ABAC 與關係條件補足真實情境

RBAC 以角色分配權限，容易理解且適合區分會員、客服與管理員；但真實授權常需要資料屬性與關係，例如客服只能看所屬區域的案件、作者能編輯草稿但不能修改已發布版本、財務匯出需要近期 MFA。這些條件不能只靠一個 isAdmin 布林值表達。

Policy 應採預設拒絕、最小權限與明確允許，並避免角色無限增生。記錄規則名稱、輸入與版本，讓拒絕能被除錯、允許能被稽核。對高影響操作可加入雙人審核或 Step-up，但它們不能取代基本物件層授權。

ROLE角色能力

會員、客服、編輯、管理員的基本動作

ATTRIBUTE主體與物件屬性

部門、方案、敏感等級、資料狀態

RELATION彼此關係

擁有者、同租戶、受指派者、審核者

CONTEXT當下條件

近期 MFA、時間、裝置、風險與批准

圖 4｜授權政策的四層 角色提供粗粒度能力，資料關係與即時狀態完成精確決策。

05

TENANT IS A HARD BOUNDARY

租戶 ID 必須來自可信身分，不可由請求自由決定

多租戶系統最危險的錯誤，是直接相信 URL、Header 或表單傳入的 tenant_id，再用它查詢資料。租戶脈絡應由已驗證 Session 或受信任服務 Token 建立，後續所有查詢、Cache Key、Object Storage Path、搜尋索引與背景工作都必須攜帶並驗證同一租戶。

管理員跨租戶支援要設計成明確能力，而不是讓平台人員默認可看全部資料。採短時授權、工單理由、Step-up、醒目介面與不可變稽核；離開支援模式後立即回到原租戶。資料庫 Row-Level Security 可作縱深防禦，但仍需正確設定連線脈絡與完整測試。

IDENTITY可信租戶脈絡

由 Session 或服務 Claims 建立，不信任自由輸入

DATA查詢帶租戶條件

讀寫、搜尋、匯出與背景工作一致

CACHEKey 含租戶

避免不同租戶共享相同快取命名空間

FILES儲存與下載隔離

Path、Bucket Policy 與下載授權共同限制

圖 5｜租戶邊界要貫穿所有儲存 任何漏掉 tenant scope 的旁路，都可能讓資料從正確 API 之外流出。

06

UUID IS NOT AUTHORIZATION

難猜的 ID 能減少偶然碰撞，不能取代 Policy

遞增數字容易讓人看出物件數量，UUID 或隨機 Slug 能降低偶然猜中其他物件的機率，適合作為縱深防禦與避免資訊洩漏；但一旦識別符出現在日誌、分享連結、Referer 或第三方系統，任何持有它的人仍不應自動取得權限。

對每一次 Read、Create、Update、Delete、Export 與 Share 都做獨立授權。分享連結若本來就是 Capability，則必須高熵、短效、可撤銷、限制動作並避免被索引；不要把永久資料庫 ID 直接當作無限期分享憑證。

IDENTIFIER找到哪一筆

ID、UUID、Slug、檔名或 Token

BENEFIT降低可預測性

減少偶然枚舉與洩漏物件數量

POLICY能不能操作

主體、動作、關係、租戶與脈絡

DENY不符合就拒絕

無論識別符是否正確，都不回傳未授權資料

圖 6｜識別符只負責定位 複雜 ID 降低猜測，Policy 才決定是否允許；兩者角色不同。

07

CHECK THE SIDE PATHS

主 API 安全，不代表匯出與背景處理也安全

越權經常藏在旁路：CSV 匯出只檢查使用者已登入、快取回傳上一個租戶結果、背景 Job 保存物件 ID 卻沒有保存發起者與授權脈絡，或 Webhook 重試時使用過大的服務帳號。這些路徑沒有瀏覽器畫面，更容易被開發流程忽略。

背景工作應保存不可變的租戶、主體與核准動作，執行時重新確認資源仍存在且授權未撤銷；輸出檔採短效下載授權並從 Web Root 隔離。Cache Key 納入所有影響可見性的維度，私有回應設定正確 Cache-Control，服務帳號則依功能拆分最小權限。

CACHE可見性維度

Key 包含使用者／租戶／角色，私有回應不共用

EXPORT下載再授權

產生與下載都要檢查，連結短效

JOB保存安全脈絡

執行時重查狀態與授權，不只保存 object_id

SERVICE最小服務權限

每種工作拆分身分、範圍與日誌

圖 7｜四條常被忘記的旁路 授權規則要跟資料一起走過同步與非同步流程。

08

TEST THE NEGATIVE SPACE

授權測試的重點，是確認「不該成功的事真的失敗」

建立 User A、User B 與管理員三個測試身分，各自擁有文件、訂單或設定。對每個 Endpoint 列出角色與動作矩陣，先驗證合法操作，再驗證 A 不能讀寫 B 的物件、一般使用者不能呼叫管理功能、另一租戶不能碰到同一識別符，以及撤銷權限後立即失效。

測試應涵蓋 UI、API、匯出、檔案下載、批次與背景工作，並確認拒絕不會洩漏物件內容。把 Policy 當成可單元測試的函式，再做整合測試確保 Router 沒漏掛。日誌記錄 Policy 名稱與拒絕原因碼，但對外只回傳適當狀態與泛化訊息。

A → A OBJECT允許合法動作

讀取與更新依 Policy 明確允許

A → B OBJECT必須拒絕

即使 ID 正確，也不能跨使用者

A → ADMIN必須拒絕

隱藏按鈕之外，伺服器阻擋功能

ADMIN → SCOPE受限管理

依職責、工單、租戶與 Step-up 限制

圖 8｜授權測試矩陣 每新增一種角色、動作或資料範圍，就補上正向與負向案例。

FIELD ASSIGNMENT

用 35 分鐘完成物件授權矩陣

在本機或測試環境建立假資料，不接觸任何真實他人資料。

  1. 00–08

    選一種物件使用訂單、文章、票券或檔案，列出擁有者、租戶與狀態。

  2. 08–17

    列角色與動作為匿名、會員、客服、管理員列出讀、改、刪、匯出與分享。

  3. 17–27

    寫負向案例建立 A／B／管理員測試帳號，確認跨使用者、跨租戶與跨角色全部拒絕。

  4. 27–35

    檢查旁路補上快取、下載、批次、背景工作與服務帳號的授權位置。

CHECK YOUR MODEL

先回答，再展開。

登入成功就能讀取網址中的任何 ID 嗎？

不能。每一筆物件和每一個動作都需要伺服器端授權。

把按鈕從前端隱藏算權限控制嗎？

不算。前端只控制介面，使用者仍能直接送請求；伺服器必須拒絕。

改用 UUID 就不會有 IDOR 嗎？

不會。UUID 降低猜中機率，但外洩或已知 UUID 仍需要完整物件層授權。

多租戶系統能相信 Header 裡的 tenant_id 嗎？

不能自由相信。租戶脈絡應由已驗證身分建立，並在所有資料路徑一致套用。

授權測試為什麼一定要兩個一般帳號？

單一帳號只能驗證合法操作，兩個帳號才能確認相同角色之間不會發生水平越權。

CHAPTER 05 / RECAP

每一筆請求，都重新做一次授權。

01

Authentication 建立身分，Authorization 針對主體、動作、物件與脈絡做決策。

02

ID、UUID 與 Slug 只定位物件，不能取代伺服器端 Policy。

03

租戶邊界必須貫穿查詢、快取、檔案、匯出與背景工作。

04

授權測試要以負向案例為核心，驗證跨使用者、跨角色與跨租戶都被拒絕。
