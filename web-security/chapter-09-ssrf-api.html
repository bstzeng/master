CONTROL SERVER-SIDE REQUESTS

SSRF、API 與伺服器端攻擊

當網站替使用者抓網址、送 Webhook 或呼叫內部 API，請求是從伺服器的網路與身分發出。這個能力若沒有目的限制，會把應用變成穿越網路邊界的代理。

70–90 分鐘8 個完整段落伺服器端請求控制授權環境限定

LEARNING OUTCOME

完成本章後，你能找出所有 Server-side Fetch 與 Callback，依固定目的或任意公網需求設計 URL 驗證、Redirect、DNS／IP 與 Egress 控制，並建立 API Schema、欄位允許、Webhook 簽章與金鑰生命週期。

SAFE PRACTICE BOUNDARY

不探測任何內網、Metadata 或陌生 API；練習只閱讀自己的架構、設定與測試 Stub。本章不列出特殊 URL Payload、IP 混淆或繞過驗證方式。

01

THE SERVER HAS DIFFERENT REACH

同一個 URL，從伺服器發出可能走到完全不同的地方

SSRF 出現在應用接受外部影響的目的地，再由伺服器主動連線，例如頭像匯入、URL 預覽、PDF 截圖、Webhook、Feed、檔案轉存或代理 API。伺服器通常能接觸內網、Loopback、雲端服務與帶有機器身分的 Endpoint，影響遠高於使用者瀏覽器直接開啟連結。

先盤點所有 HTTP Client、SDK、下載器、Webhook 與 Redirect Follow，記錄誰控制 Scheme、Host、Port、Path、Header 和 Body，以及執行服務能連到哪些網路。將「解析 URL」「解析 DNS」「建立連線」「跟隨 Redirect」視為連續安全決策，而不是只做一次字串檢查。

USER提供目的

URL、網域、Webhook 或匯入來源

SERVER代為連線

使用伺服器 DNS、Route、Cookie、Header 或 IAM

BOUNDARY目的與 Egress Policy

只允許業務所需協定、網域、IP 與 Port

TARGET外部或內部服務

回應大小、Redirect、Timeout 與內容型別受限

圖 1｜伺服器有更大的網路視野 SSRF 的核心是利用應用的網路位置與機器身分，不一定需要回傳完整內容。

02

ALLOWLIST WHEN POSSIBLE

固定合作服務與任意公網 URL，需要不同設計

若應用只需呼叫已知付款、HR 或圖片服務，最安全是根本不接受完整 URL，而由使用者選擇服務代碼，伺服器映射到固定 Scheme、Host、Port 與 Path。這讓 Allowlist 清楚、可測試，也能在網路層只開必要 Route。

若產品必須抓取任意公網網址，風險更高：只允許 HTTP／HTTPS，禁止使用者控制敏感 Header，解析所有 A／AAAA 結果並拒絕非公網目的，限制 Port，不自動跟隨 Redirect 或每跳重新驗證，且下載大小、時間與回應型別都有上限。高風險功能可改為隔離 Fetch Service，不與主應用共享憑證。

CASE A已知目的

服務代碼映射固定 URL；應用與網路雙層 Allowlist

NETWORK只開必要 Route

固定 DNS、IP、Port、TLS 與 Client Identity

CASE B任意公網

限制 Scheme、Port、DNS／IP、Redirect、大小與時間

ISOLATE專用 Fetcher

無內網、無 Secret、低權限、受控 Egress

圖 2｜先依需求選模型 能映射固定目的就不要接受完整 URL；任意 Fetch 則需要隔離與多層驗證。

03

VALIDATE THE CONNECTED DESTINATION

驗證輸入字串還不夠，真正連線目的也必須符合政策

使用成熟 URL Parser，拒絕不需要的 Scheme、Userinfo、非標準 Port 與無法正規化的 Host；以平台 IP 函式分類 IPv4／IPv6，不自己寫脆弱正規表示式。解析網域後檢查所有 IP 都符合允許政策，並確保實際連線仍使用已驗證結果，降低解析與連線之間被替換的風險。

Redirect 會讓已允許的第一個 URL 指向新目的，因此優先關閉自動跟隨；若業務需要，每一跳重新驗證 Scheme、Host、Port 與解析 IP，限制跳數並移除敏感 Header。HTTP Client 要設定 Connection、Read、Total Timeout、最大回應大小與 Content-Type，不把上游錯誤細節原樣轉回使用者。

PARSE標準 URL Parser

Scheme、Host、Port、Userinfo 與正規化

RESOLVE所有 A／AAAA

使用平台 IP 分類，拒絕不符合目的政策

CONNECT受控 Egress

連線到已驗證目的，限制 Header、Timeout 與大小

REDIRECT每跳重驗證

優先關閉；需要時限制跳數並重新套 Policy

圖 3｜驗證真正連線目的 安全決策要綁定連線，不只綁定一開始看見的字串。

04

ENFORCE AT THE NETWORK

應用驗證會出錯，網路層必須阻止不必要目的地

Egress Firewall、VPC Route、Service Mesh 或 Proxy 應只允許服務需要的目的、Port 與 DNS，拒絕其他內網、管理面和 Link-local。把 URL Fetch 放在獨立網段與專用身分，讓它即使被錯誤使用也接觸不到主資料庫、控制面與 Secret。

雲端執行環境應採供應商最新 Metadata 保護、限制 Pod／Task 的 IAM 權限，避免把長期 Cloud Credential 注入處理外部 URL 的服務。網路日誌要能識別來源服務與拒絕目的；若發現應用嘗試連到不在業務清單的內部範圍，應視為程式缺陷或安全事件調查。

APP目的驗證

固定映射或完整公網 URL Policy

EGRESS集中代理

記錄目的、限制協定、Port、DNS、大小與時間

NETWORK分段與拒絕

Fetch Service 不可達內網、控制面與管理服務

IAM最小機器身分

無長期 Secret，只能執行必要雲端動作

圖 4｜SSRF 的縱深防禦 即使應用層 Parser 或 Allowlist 失誤，網路與身分仍限制最壞影響。

05

TREAT THE API AS A CONTRACT

API 每個 Endpoint 都要驗證身分、物件、欄位與資源成本

REST API 只提供 HTTPS，非公開 Endpoint 在每次請求驗證 Token 的簽章、Issuer、Audience、時間與 Scope，並做物件層授權。Gateway 可以集中 TLS、Rate Limit 與基本 Token 驗證，但服務仍要在本地完成資料與業務授權，不能把 Gateway 當唯一安全邊界。

請求與回應都使用明確 Schema：拒絕額外欄位、限制型別、長度、集合數、分頁、巢狀深度與 Content-Type。錯誤回應穩定且不洩漏內部堆疊；版本與 Endpoint 有擁有者、資料分類和下線日，避免舊 API 留著較弱的驗證與控制。

TRANSPORTHTTPS

保護傳輸並驗證服務端，拒絕明文 Endpoint

IDENTITYToken Claims

簽章、Issuer、Audience、時間、Scope 與撤銷

AUTHZ物件與功能

每個 Endpoint、動作、物件與租戶都做決策

SCHEMA資料契約

欄位、型別、大小、深度與額外屬性

圖 5｜API 的五道決策 Gateway 提供共同控制，服務端仍負責最終物件、欄位與商業授權。

06

MAP INPUT EXPLICITLY

Client 可以送來的欄位，必須由 Endpoint 明確定義

許多框架能把 JSON 或表單自動綁定到 Domain Model，若直接用 req.body 更新 User、Order 或 Project，Client 可能傳入畫面沒有顯示、但模型真實存在的欄位，例如角色、狀態、擁有者、折扣或審核結果。這是 Mass Assignment：資料繫結過度暴露了內部物件能力。

為每個 Use Case 建立專用 DTO／Request Schema，只列允許欄位，再逐欄映射到 Domain Command。敏感欄位由伺服器依目前主體、狀態機與 Policy 計算；拒絕或忽略額外屬性的策略要一致並可測試。回應 DTO 也要明確，避免序列化整個內部物件而洩漏 Secret、內部 ID 或敏感 Metadata。

RISKYreq.body → Model

額外欄位可能覆寫角色、狀態、租戶或擁有者

MODEL內部能力過大

資料庫欄位和方法不應自動成為 Client 介面

SAFERequest DTO

只列用例需要的欄位、型別與限制

MAP逐欄建立 Command

敏感值由伺服器 Policy 與狀態機決定

圖 6｜API 欄位也需要授權 Endpoint 應只接受此用例需要的欄位；內部模型不是公開 API 契約。

07

VERIFY BOTH DIRECTIONS

接收要驗證來源與重播，發送要限制目的與 Secret

接收 Webhook 時驗證供應商簽章或 Mutual TLS，簽章涵蓋原始 Body、時間戳與事件 ID；限制允許時間窗，使用 Idempotency／Replay Store 避免同一事件重複執行。先驗證完整性，再解析 Body 與執行商業授權，並快速回應後交由受控 Queue 處理。

發送 Webhook 時，目的 URL 驗證適用 SSRF 控制；每個訂閱者使用獨立 Secret，可輪替、撤銷且不顯示完整值。重試採上限與退避，避免被慢目的拖垮；Payload 只包含必要資料，日誌記錄事件、目的代碼、結果和延遲，不記錄 Secret 或不必要個資。

INBOUND驗證簽章

原始 Body、時間戳、事件 ID 與獨立 Secret

REPLAY冪等與時間窗

重複事件不重複造成商業影響

OUTBOUND限制目的

套用 SSRF URL／DNS／Egress Policy

DELIVERY受控重試

上限、退避、Timeout、最小 Payload 與稽核

圖 7｜Webhook 是雙向邊界 接收端關心真偽與重播；發送端關心 SSRF、資料最小化、重試與 Secret 生命週期。

08

INVENTORY EVERY OUTBOUND CALL

不知道服務會連去哪裡，就無法設定真正的 Egress Policy

建立 Outbound Request Inventory：功能、程式位置、擁有者、目的類型、允許 Scheme／Host／Port、DNS、Redirect、Header、機器身分、回應大小、Timeout、重試、資料分類與日誌。特別找出通用 HTTP Client、使用者 URL、Webhook、圖片抓取、文件轉換與第三方 SDK。

為每個功能測試拒絕非允許 Scheme、私有或保留目的、不同 Port、Redirect 到未允許目的、超大與慢回應、錯誤 Content-Type、額外 API 欄位和重播 Webhook。測試使用本機 Stub 與保留測試資料，不觸碰真實內網或 Metadata；Egress 拒絕事件要能對應服務版本和請求 ID。

DESTINATION允許去哪裡

Scheme、Host、Port、IP 類型、Redirect 與 DNS

IDENTITY帶什麼權限

Header、Token、mTLS、IAM 與 Secret 生命週期

RESOURCE最多花多少

大小、連線／讀取／總 Timeout、重試與併發

OBSERVE如何發現越界

Egress Log、拒絕、延遲、錯誤與事件關聯

圖 8｜Outbound Request Inventory 把每個外連能力變成明確契約，才能收斂網路權限並安全回歸。

FIELD ASSIGNMENT

用 45 分鐘建立 Outbound Request Inventory

只閱讀自己的程式與平台設定，測試使用本機 Stub；不要嘗試連線到真實內網或 Metadata。

  1. 00–12

  2. 12–24

  3. 24–35

CHECK YOUR MODEL

先回答，再展開。

只允許 https:// 就能防 SSRF 嗎？

不能。仍要驗證 Host、Port、解析 IP、Redirect、實際連線目的與 Egress。

Gateway 驗證 Token 後，後端服務還要授權嗎？

要。服務需要依 Endpoint、物件、動作與租戶做最終決策。

為什麼不能把 req.body 直接更新 Model？

可能接受 Client 不應控制的角色、狀態、擁有者等欄位，形成 Mass Assignment。

Webhook 有簽章就不需要防重播嗎？

需要。合法簽章的舊事件可能被重送，應驗證時間窗與事件 ID，並採冪等處理。

Egress Firewall 為什麼不能被應用驗證取代？

應用 Parser 或規則可能失誤，網路層提供獨立的最壞影響限制。

CHAPTER 09 / RECAP

不要讓伺服器替外部輸入跨越網路邊界。

01

SSRF 利用應用的網路位置與機器身分；先盤點所有 Server-side Fetch 與 Callback。

02

固定目的使用映射與 Allowlist；任意公網 Fetch 需要完整 URL、DNS／IP、Redirect 與隔離控制。

03

API 每次請求驗證 Token、物件授權與 Schema，使用 DTO 防止額外欄位改變內部模型。

04

Webhook 接收驗證簽章與重播，發送限制目的、資料、Secret、Timeout 與重試。
