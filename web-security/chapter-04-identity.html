DEFEND THE IDENTITY

帳號、密碼與登入攻擊

登入不是只有一個密碼欄位，而是一條從註冊、驗證、Session、敏感操作到帳號復原的生命週期。只要其中一段比其他段弱，攻擊者就會從那裡取得同樣的帳號控制權。

70–90 分鐘8 個完整段落身分生命週期授權環境限定

LEARNING OUTCOME

完成本章後，你能區分暴力猜測、密碼噴灑與憑證填充，檢查密碼儲存、登入回應、MFA、Session、敏感操作與帳號復原，並產出一份自己的身分流程控制表。

SAFE PRACTICE BOUNDARY

練習只檢查自己的程式、測試帳號與既有日誌；不收集外洩帳密、不嘗試陌生帳號，也不提供密碼清單、繞過 MFA 或竊取 Session 的方法。

01

IDENTITY IS A LIFECYCLE

登入成功只是開始，不是安全終點

一個帳號從註冊或邀請開始，接著經過憑證綁定、登入、建立 Session、變更資料、執行高風險操作、登出、復原與停用。攻擊者取得控制權不一定要猜中密碼：弱重設連結、未撤銷 Session、客服驗證不足或離職帳號未停用，都能到達相同結果。

防守者應把每一個能改變「這個人是誰」或「這個人能做什麼」的流程放在同一張圖上，標出憑證、權限、有效期限、通知、日誌與復原方式。只有登入頁很強、復原流程卻只問可猜答案，等於替強門鎖留了一扇沒上鎖的側門。

01 / ENROLL建立身分

驗證來源、綁定憑證、記錄擁有者

02 / AUTH確認身分

密碼、Passkey 或多因素驗證

03 / SESSION延續身分

短生命週期、輪替、撤銷與裝置可見性

04 / RECOVER安全復原

一次性 Token、重新驗證、全端失效

圖 1｜身分生命週期 每個階段都要維持同等強度，並能撤銷前一階段留下的權限。

02

KNOW THE ATTACK SHAPE

同樣是登入失敗，背後可能是三種不同模式

暴力猜測通常針對單一帳號嘗試許多候選密碼；密碼噴灑則以少數常見密碼碰許多帳號；憑證填充使用其他網站外洩的帳號密碼組合，利用使用者重複使用密碼。三者在帳號數、密碼數、來源分布與時間節奏上不同，因此單靠「一個 IP 連錯五次就鎖帳號」容易漏掉分散式嘗試，也可能被濫用來鎖住真實使用者。

控制要同時觀察帳號、來源、裝置、網段、失敗率與成功後行為。漸進延遲、帳號與來源雙軸限速、風險式 MFA、已外洩密碼阻擋和異常通知應疊加使用。錯誤訊息則保持一致，避免直接透露帳號是否存在，但內部日誌仍要保留可分析的原因。

ONE ACCOUNT多個密碼

可能是集中式暴力猜測；觀察帳號維度

MANY ACCOUNTS少數密碼

可能是密碼噴灑；觀察跨帳號共通值

LEAKED PAIRS帳密組合

可能是憑證填充；MFA 與外洩密碼阻擋重要

DEFENSE多訊號控制

限速、風險評估、告警與使用者通知

圖 2｜登入攻擊的形狀 看模式而不是只看單一 IP，才能同時降低漏報與誤鎖。

避免可被濫用的鎖定

永久鎖定帳號會讓攻擊者用失敗登入造成拒絕服務。優先使用短暫延遲、風險式挑戰與安全復原，並監控對多帳號的共同嘗試。

03

MAKE PASSWORDS USABLE

長度、封鎖清單與密碼管理器，比複雜格式更實際

現代密碼政策應允許長密碼與密碼片語、Unicode、空白和密碼管理器貼上，不應強迫使用者以固定週期更換或套用難記的字元組合。NIST SP 800-63B-4 要求單因素密碼至少 15 個字元；若密碼只作為多因素流程的一部分，最低可為 8 個字元，並要求用常見或已外洩值的封鎖清單檢查。

前端強度提示只是協助選擇，真正規則必須由伺服器執行。應設定足夠大的最大長度且不靜默截斷，錯誤訊息要可理解，密碼重設後需讓既有高風險 Session 失效。若能提供 Passkey 或抗釣魚驗證器，應把它當成降低密碼依賴的替代方案，而不是新增另一個脆弱備援流程。

AVOID固定週期強制更換

容易產生可預測變形，沒有事件不必任意輪替

AVOID僵硬字元配方

大寫小寫數字符號不保證不可猜

PREFER足夠長度

允許長片語、貼上與密碼管理器

PREFER外洩值封鎖

比對常見與已知遭洩漏的密碼

圖 3｜密碼政策的取捨 安全政策要讓使用者能採用密碼管理器和長片語，並在伺服器端阻擋已知弱值。

04

HASH, DO NOT ENCRYPT

資料庫失守時，密碼仍必須難以還原

密碼不應明文儲存，也不應用可逆加密保護。伺服器只保存由專用慢速、具記憶體成本的雜湊函式產生的驗證值，並為每個密碼加入唯一 Salt。OWASP 優先建議 Argon2id；環境限制時可依官方指引選擇 scrypt、bcrypt 或 PBKDF2，參數則要定期依硬體成本重新評估。

不要自行發明演算法，也不要只做一次 SHA-256。驗證時使用框架提供的安全比較函式；當使用者成功登入且舊雜湊參數落後，可在該次流程平滑升級。Pepper 若採用，必須與資料庫分離放在 Secret 管理系統，且要預先規劃 Pepper 外洩後如何要求重設。

INPUT使用者密碼

透過 TLS 傳輸，伺服器限制合理長度

KDFArgon2id

每筆唯一 Salt，加上可調整成本

STORE雜湊與參數

不保存原文；Pepper 與資料庫分離

VERIFY安全比較

成功時可升級舊參數，不回傳細節

圖 4｜密碼只作驗證，不作解密 使用成熟函式庫，讓資料庫外洩不會直接變成所有使用者密碼外洩。

05

ADD AN INDEPENDENT FACTOR

第二因素必須真的獨立，並保護最關鍵的動作

MFA 的價值來自不同類型證明，而不是再問一個知識題。密碼加安全問題仍然都是「知道的資訊」，不能算獨立因素。Passkey 或安全金鑰能提供較佳抗釣魚能力；Authenticator App 的一次性碼通常優於簡訊，但仍需要安全綁定、復原碼、遺失處理和替換流程。

不一定每個低風險動作都反覆挑戰，但管理員、付款、變更電子郵件、停用 MFA、下載敏感資料與建立 API Key 等操作應要求近期驗證或 Step-up。新增或替換因素本身就是高風險事件，必須驗證現有因素、通知使用者並記錄裝置、時間與執行者。

BASE一般登入

密碼或 Passkey，產生最低必要 Session

SIGNAL風險訊號

新裝置、異常地點、敏感角色與行為

STEP-UP近期再驗證

抗釣魚因素或額外獨立證明

AUDIT通知與日誌

因素新增、移除、失敗與復原皆可追蹤

圖 5｜MFA 與 Step-up 先建立 Session，再依行為風險要求更強證明；因素變更也屬於敏感操作。

06

PROTECT THE SESSION

密碼驗證一次，Session 會代表使用者很久

登入成功後，網站通常用不可預測的 Session ID 或受驗證 Token 表示身分。任何持有有效 Bearer Token 的人，都可能被系統當成使用者本人，因此不能把完整 Token 放進 URL、前端日誌或不受信任儲存。Cookie 型 Session 應使用 Secure、HttpOnly、適當 SameSite 與窄化 Domain／Path，並只透過 HTTPS。

登入與權限提升後要輪替 Session ID，避免固定攻擊；同時設定閒置與絕對到期、伺服器端撤銷、裝置清單與全部登出能力。JWT 也不是自動安全：仍要驗證簽章、Issuer、Audience、時間和演算法，並處理撤銷與金鑰輪替。短效 Access Token 配合受保護的 Refresh Token，可縮小單次外洩時間窗。

ISSUE登入後建立

高熵識別、伺服器記錄或受驗證 Token

CARRY安全傳遞

HTTPS；Cookie 使用 Secure、HttpOnly、SameSite

ROTATE權限改變時輪替

登入、Step-up、角色變更後換新識別

REVOKE可立即失效

登出、重設密碼、異常事件與停權

圖 6｜Session 是第二把鑰匙 Session 風險獨立於密碼；生命週期、儲存位置與撤銷能力缺一不可。

07

RECOVERY IS AUTHENTICATION

忘記密碼流程本質上是在重新發放帳號控制權

重設請求的回應時間與內容應盡量一致，不揭露帳號是否存在，也不能因大量請求讓特定帳號被永久鎖住。重設 Token 要由安全亂數產生、單次使用、短效且安全儲存，透過已驗證的旁路傳送；伺服器只有在 Token 驗證成功後才真正改變密碼。

重設完成後應通知帳號持有人、使其他 Session 與高風險 Token 失效，並要求重新登入。客服人工復原和 MFA 遺失流程也要列入同一威脅模型：需要多項獨立證據、權限分離與稽核，不能因使用者著急就讓客服越過所有控制。安全問題通常容易被查到，不適合作為唯一復原因素。

REQUEST一致回應

不揭露帳號存在，限制濫用

TOKEN單次且短效

安全亂數、安全儲存、旁路傳送

CHANGE驗證後才修改

設定新憑證，避免自動登入

INVALIDATE撤銷舊權限

失效其他 Session，通知並稽核

圖 7｜帳號復原也是高風險登入 重設連結只是短暫授權，不應直接成為長期 Session，也不能繞過通知與撤銷。

08

MEASURE THE CONTROL

把登入防線做成可觀察、可測試的系統

至少記錄登入成功與失敗、帳號雜湊識別、來源網路、裝置或 Client 訊號、MFA 結果、Session 建立與撤銷、密碼與因素變更、重設請求和管理員代操作。日誌不要保存密碼、完整 Token 或重設連結，並使用事件 ID 串起同一流程。

建立控制表時，把每個流程列成「入口、需要證明、限速維度、成功後權限、通知、事件與撤銷」。測試不只驗證正常登入，也要驗證不存在帳號的回應一致、重設 Token 重用會失敗、登出後 Session 無效、角色提升會輪替 Session，以及管理員一定使用 MFA。

PREVENT降低成功機率

外洩密碼阻擋、MFA、限速與安全儲存

DETECT看見異常模式

跨帳號、來源、裝置與成功後行為

RESPOND快速停止權限

撤銷 Session、停用憑證、通知使用者

RECOVER安全取回帳號

短效 Token、獨立驗證、完整稽核

圖 8｜身分控制表 每個流程同時需要預防與事後能力，才能在憑證真的外洩時縮小影響。

FIELD ASSIGNMENT

用 40 分鐘畫出自己的登入生命週期

只使用自己的測試帳號、程式設定與既有日誌；不輸入真實密碼到課程筆記。

  1. 00–10

    畫流程列出註冊、登入、Session、敏感操作、登出、重設、MFA 遺失與停權。

  2. 10–20

    檢查儲存確認密碼函式、參數、Cookie 屬性、Session 到期與伺服器撤銷。

  3. 20–30

    檢查濫用控制記錄帳號與來源雙軸限速、MFA、外洩密碼封鎖和一致回應。

  4. 30–40

    補上偵測與復原挑三個事件建立日誌、通知、Session 失效與負責人。

CHECK YOUR MODEL

先回答，再展開。

密碼加安全問題算 MFA 嗎？

不算，兩者都是使用者知道的資訊。MFA 需要不同類型的獨立證明，例如持有的安全金鑰或裝置。

為什麼不能只依 IP 限制登入？

攻擊可能分散來源，共用網路也可能讓真實使用者被連帶限制。要同時看帳號、來源、裝置、行為與時間。

密碼可以用 AES 加密後儲存嗎？

不應。密碼驗證通常不需要還原原文，應使用 Argon2id 等專用慢速雜湊與唯一 Salt。

使用 JWT 是否不需要處理登出？

不是。JWT 仍需短效、驗證 Claims、保護金鑰並設計撤銷或輪替策略，尤其是 Refresh Token。

重設密碼後最容易忘記什麼？

使既有 Session、Refresh Token 和高風險授權失效，並通知使用者檢查是否為本人操作。

CHAPTER 04 / RECAP

守住身分，必須守住整個生命週期。

01

登入攻擊要依帳號、來源與行為形狀分析，單一 IP 鎖定不足以應對分散式嘗試。

02

密碼政策重視長度、外洩值封鎖與安全雜湊，並支援密碼管理器。

03

MFA、Step-up 與 Session 生命週期共同決定登入後權限是否安全。

04

重設與人工復原本質上是重新發放控制權，強度不能低於一般登入。
