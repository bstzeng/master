THE BROWSER IS A BOUNDARY

XSS、CSRF 與瀏覽器攻擊

瀏覽器同時是 HTML 解譯器、憑證攜帶者與跨來源守門員。XSS、CSRF、CORS 和 Clickjacking 看似不同，實際上都在利用網站錯誤理解瀏覽器的信任邊界。

80–100 分鐘8 個完整段落瀏覽器信任邊界授權環境限定

LEARNING OUTCOME

完成本章後，你能區分 XSS 與 CSRF，依 HTML、Attribute、URL、JavaScript 等輸出脈絡選擇編碼，使用框架安全預設、Sanitization 與 CSP，並檢查 Cookie、CSRF Token、SameSite、CORS 與防嵌入設定。

SAFE PRACTICE BOUNDARY

本章不提供可執行的 XSS Payload、誘導表單或繞過瀏覽器控制技巧。練習只檢查自己的模板、Header 與測試請求，使用無害文字驗證內容被顯示為資料。

01

READ THE BROWSER MODEL

瀏覽器會解譯內容，也會自動替使用者攜帶狀態

瀏覽器根據 Content-Type 與文件脈絡解析 HTML、CSS、JavaScript、URL 和 SVG；同時依 Domain、Path、SameSite 等規則自動帶上 Cookie，並以 Same-Origin Policy 限制不同 Origin 的腳本讀取彼此資料。網站安全設計必須以這些真實行為為基礎，而不是假設使用者只會按畫面上的按鈕。

Origin 由 Scheme、Host 與 Port 組成；Site 則是另一組較寬的瀏覽器概念。CORS 放寬跨 Origin 讀取，SameSite 影響跨 Site Cookie，兩者不能互換。先畫出頁面、API、CDN、登入網域與第三方 Script 的 Origin，才能知道哪一個控制應放在哪裡。

ISOLATE同源政策

02

DATA BECOMES BROWSER CODE

XSS 發生在不可信資料進入可執行的瀏覽器脈絡

Stored XSS 會把危險內容保存後送給其他使用者，Reflected XSS 由當次請求反射，DOM XSS 則由前端程式在瀏覽器內把可控資料送進危險 Sink。共同條件是攻擊者能影響內容，且瀏覽器把它當成標記、Script、事件、URL 或其他可執行結構，而不是純文字。

防守先利用框架 Auto-escape 與安全模板，把變數放在明確的安全位置；避開 innerHTML、document.write、eval 類 Sink 和框架的 unsafe escape hatch。資料若需要顯示成純文字，使用 textContent 等安全 Sink；若業務真的允許少量 HTML，使用成熟 Sanitizer 與嚴格允許設定。

SOURCE不可信資料

URL、表單、API、資料庫與第三方內容

CONTEXT輸出位置

HTML Body、Attribute、URL、CSS 或 JavaScript

CONTROL編碼或 Sanitization

依脈絡處理；優先使用框架安全預設

SINK安全顯示

textContent、受保護模板與允許的 DOM API

03

ENCODE FOR THE CONTEXT

HTML 編碼不是萬用：不同 Parser 需要不同規則

同一段資料放在 HTML Body、Quoted Attribute、URL Query 或 JavaScript 字串時，瀏覽器使用不同語法解析；防禦也不同。最安全做法是不要把不可信資料放進 Script、Style、事件處理器、標籤名稱或未加引號 Attribute 等危險脈絡，並讓框架與專用 Encoder 依實際位置處理。

URL 值需要先限制 Scheme 與目的，再做 URL Encoding，嵌入 Attribute 時還要由模板處理 Attribute 編碼。JSON API 使用正確 application/json Content-Type，避免被當成 HTML；顯示富文字時先 Sanitization，再把結果送進唯一受控的渲染元件。把安全規則封裝成元件，比要求每個畫面作者記住所有細節更可靠。

URL限制 Scheme 再編碼

JAVASCRIPT盡量不插值

以 JSON 資料與安全 API 傳遞，避開可執行脈絡

04

DEPLOY DEFENSE IN DEPTH

CSP 能限制資源與 Script，但不能替代安全輸出

Content-Security-Policy 由伺服器告訴瀏覽器哪些 Script、Style、Image、Frame 與連線來源可用。嚴格 CSP 常用每次回應的 Nonce 或 Build-time Hash 搭配 strict-dynamic，並設定 object-src 'none'、base-uri 'none'；frame-ancestors 控制哪些網站能嵌入頁面。

CSP 應先以 Report-Only 收集違規、整理必要來源，再逐步 Enforcement；不要直接用大量 wildcard、unsafe-inline 或長期固定 Nonce 讓政策失去意義。它是 XSS 的縱深防禦：即使某處輸出失誤，也提高任意 Script 執行難度，但根因仍需以安全模板、編碼和 Sanitization 修正。

05

PROVE USER INTENT

伺服器必須分辨「瀏覽器送出」與「使用者真的同意」

CSRF 利用瀏覽器在跨站請求中可能自動帶上 Session Cookie，讓已登入使用者的瀏覽器執行非預期的狀態變更。防守先確保 GET、HEAD 等安全方法不改變狀態，再使用框架內建 CSRF 保護，對 POST、PUT、PATCH、DELETE 驗證與 Session 綁定的不可預測 Token。

SameSite Cookie 是重要縱深防禦，但不能涵蓋所有相容性與同 Site 子網域風險；高影響操作還要檢查 Origin／Fetch Metadata、要求近期再驗證和使用者確認。CSRF Token 不放 URL 或日誌，也不能只檢查「欄位存在」；伺服器必須驗證它與目前 Session 的關聯。

REQUEST狀態變更

POST／PUT／PATCH／DELETE，不以 GET 改資料

BROWSERSameSite 與來源

減少跨站 Cookie，檢查 Origin／Sec-Fetch-Site

TOKENSession 綁定證明

不可預測、不進 URL、伺服器完整驗證

06

STORE CREDENTIALS DELIBERATELY

Cookie 與 Web Storage 的風險不同，沒有萬用答案

HttpOnly Cookie 可避免 JavaScript 直接讀取 Session，但瀏覽器會依規則自動附帶，所以需要 SameSite 與 CSRF 防護；localStorage 不會自動送出，卻能被同 Origin 的 XSS 讀取，而且通常長期保留。敏感 Bearer Token 不應因實作方便就放進任何前端可讀的持久儲存。

以網站架構決定模式：傳統 Web App 常用 Secure、HttpOnly、SameSite 的伺服器 Session Cookie；SPA 可採 Backend-for-Frontend，把長期憑證留在伺服器端。無論模式，都要限制 Domain、Path、生命週期與權限，避免 Token 進 URL、錯誤訊息、Analytics 或 Client Log。

COOKIE可設 HttpOnly

Script 不直接讀取；瀏覽器會依規則自動攜帶

COOKIE RISK需要 CSRF 防護

SameSite、Token、Origin 與狀態方法共同控制

WEB STORAGE前端可讀

不自動附帶，但同 Origin XSS 可讀取

PREFER縮小前端憑證

短效、最小 Scope、避免持久儲存與 URL

07

CONTROL CROSS-ORIGIN ACCESS

CORS 是瀏覽器讀取許可，不是 API 身分驗證

CORS 回應 Header 告訴瀏覽器哪些 Origin 的 Script 可以讀取回應。它不會替 API 驗證身分，也不能阻止非瀏覽器 Client 直接送請求。若允許 Credentials，就不能使用 wildcard Origin；伺服器應以精確 Allowlist 比對完整 Origin、處理 Vary: Origin，並避免把輸入 Origin 無條件反射。

Clickjacking 則利用透明或誤導 Frame 讓使用者點擊真正網站。使用 CSP frame-ancestors 限制允許嵌入的父頁；舊系統可搭配 X-Frame-Options。高風險操作仍需清楚確認與近期驗證，因為防 Frame 不等於所有 UI 誘導都被消除。

AUTH呼叫者是誰

Session、Token 或 Client Credential 的驗證

CSRF是否為預期動作

Cookie 型狀態變更的意圖證明

FRAME誰能嵌入頁面

08

VERIFY IN THE BROWSER

把模板、Header、Cookie 與跨來源行為做成回歸測試

建立頁面類型清單：公開內容、登入、帳號設定、管理頁、JSON API、下載與第三方嵌入。逐類記錄輸出資料來源、使用的安全元件、CSP、Content-Type、Cookie、CSRF、CORS 與 Frame Policy。不要只在首頁檢查 Header，錯誤頁、Redirect 和 CDN 快取回應也要一致。

自動測試可用無害字串確認特殊字元顯示為文字、不新增 DOM 節點；狀態變更缺少或帶錯 CSRF Token 時失敗；未允許 Origin 無法讀取含 Credentials 的回應；敏感頁無法被陌生 Frame 嵌入。CSP 先觀察報告並逐步收緊，違規事件要能對應版本與頁面。

STATE動作有意圖

CHECK YOUR MODEL

先回答，再展開。

CSP 可以取代輸出編碼嗎？

不能。CSP 是縱深防禦；根因仍要用安全模板、依脈絡編碼與必要 Sanitization 修正。

SameSite=Strict 就不需要 CSRF Token 嗎？

不應這樣假設。相容性、同 Site 子網域與業務流程仍可能需要 Token、Origin 與再驗證。

CORS 能阻止 curl 呼叫 API 嗎？

不能。CORS 是瀏覽器讀取政策，API 仍需認證、授權、限速與驗證。

HttpOnly Cookie 能阻止 XSS 做任何事嗎？

不能。它降低 Script 直接讀取 Cookie 的風險，但 XSS 仍可能以使用者身分發起操作或讀取頁面資料。

為什麼不可信資料不應放進事件 Attribute？

那是可執行 JavaScript 脈絡，即使一般 HTML 編碼也可能不足，應重新設計為安全事件綁定。

CHAPTER 07 / RECAP

先理解瀏覽器，才知道控制放在哪裡。

01

XSS 是資料進入可執行瀏覽器脈絡；依輸出位置使用安全模板、編碼或 Sanitization。

02

CSP 限制可執行資源，是 XSS 的第二層保護，不取代根因修正。

03

CSRF 利用自動攜帶 Cookie，狀態變更需要 Token、SameSite、來源訊號與授權。

04

CORS、認證、CSRF 與 frame-ancestors 各有責任，不能互相替代。
