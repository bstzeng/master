PROTECT AVAILABILITY

DDoS、機器人與資源濫用

可用性不是「伺服器還活著」而已，而是合法使用者能在可接受時間與成本內完成關鍵任務。大量流量、昂貴請求、機器人和功能濫用都可能讓服務失去這個能力。

60–80 分鐘8 個完整段落可用性工程授權環境限定

LEARNING OUTCOME

完成本章後，你能定義服務的關鍵任務與容量預算，區分容量型、應用型與業務濫用，找出昂貴 Endpoint，設計多維度限速、Cache、Queue、Backpressure、配額、降級和 DDoS Runbook。

SAFE PRACTICE BOUNDARY

本章不產生攻擊流量、不做壓力測試或 Bot 模擬到任何線上系統。練習只閱讀既有 Metrics、用試算估算容量，實際 Load Test 必須在隔離環境與明確變更窗口另行授權。

01

AVAILABILITY IS A USER OUTCOME

服務在線，關鍵任務仍可能已經失敗

首頁回 200 不代表使用者能登入、付款、查詢或下載。為每個關鍵任務定義 SLI：成功率、延遲、正確性與新鮮度，再設定可接受 SLO 與 Error Budget。容量規劃同時估算正常尖峰、行銷活動、重試風暴、第三方變慢與單一元件故障。

可用性與成本相連：若每次查詢觸發昂貴資料庫掃描、第三方 API 或大型模型推論，少量請求也能耗盡預算。把每個 Endpoint 的 CPU、Memory、DB Query、Outbound Call、Bytes 與金額視為資源帳，優先保護登入、核心讀取與交易完成等最重要路徑。

SUCCESS任務完成率

登入、付款、查詢與資料保存是否正確成功

LATENCY可接受時間

P95／P99 與 Queue Delay，不只平均值

COST單位資源成本

CPU、DB、第三方、頻寬、儲存與金額

RECOVERY故障後恢復

RTO、RPO、降級、回滾與替代路徑

圖 1｜可用性是一組使用者結果 容量與防濫用要以關鍵任務為中心，而不是只看主機 CPU。

02

NAME THE BOTTLENECK

大量封包、昂貴請求與業務濫用，防法完全不同

容量型 DDoS 目標是頻寬或連線，通常需要 ISP、Anycast CDN、DDoS 清洗與 Edge 防護；應用層 DoS 使用看似合法但昂貴的 HTTP 功能耗盡 Thread、DB Pool 或第三方額度；業務濫用則大量註冊、搶票、寄信、爬取或套用優惠，可能流量不大卻直接造成成本和公平性問題。

先定位最先飽和的資源：Ingress、Connection、Worker、Queue、Database、Cache、Disk、Third-party 或預算。WAF 規則只能處理部分已知形狀，不能取代容量、產品配額與安全架構。不同壓力要有不同 Owner、Metric、Threshold 與降級策略。

VOLUMETRIC頻寬與連線

依賴 CDN、ISP、Anycast、Edge 與清洗能力

APPLICATION昂貴 Endpoint

限制並行、查詢成本、Timeout、Cache 與 Queue

BUSINESS功能濫用

帳號、付款工具、裝置與業務規則配額

FAILURE依賴與成本

Circuit Breaker、Budget、降級與人工處置

圖 2｜先找瓶頸再選控制 把所有異常流量都叫 DDoS，會讓團隊在錯誤層級部署控制。

03

MEASURE COST PER REQUEST

平均流量不高，也可能因單次成本不受限而失效

盤點搜尋、報表、匯出、上傳、圖片轉換、密碼雜湊、登入、寄信、Webhook、GraphQL 與第三方查詢。記錄每次最大 Input、結果數、DB Rows、Query Time、外部呼叫、CPU、Memory、Bytes、Timeout 和可否重試，找出成本會隨輸入線性或更快成長的路徑。

產品 Contract 應限制分頁、Filter 數、搜尋範圍、日期區間、Graph 深度、檔案展開、並行工作與每租戶總額；昂貴工作非同步化並顯示狀態。資料庫使用索引、Query Timeout、Connection Pool 與只讀 Replica，但要保留 Backpressure，不能讓 Queue 無限吸收直到磁碟填滿。

INPUT大小與複雜度

頁數、日期、深度、Filter、檔案與批次上限

APPCPU／Memory

Concurrency、Deadline、隔離 Pool 與取消

DATARows／Connections

索引、Query Timeout、結果上限與 Pool

DEPENDENCY外部成本

Timeout、Circuit Breaker、Cache、Quota 與預算

圖 3｜每次請求都有成本預算 在每一層限制最大工作量，避免單一合法參數組合產生無界成本。

04

LIMIT FAIRLY

IP 只是訊號之一，真正公平要理解身分與功能成本

Edge Rate Limit 適合在流量進入應用前限制明顯異常，但共用 NAT、行動網路與分散式 Bot 讓 IP 不能代表唯一使用者。應依 Endpoint 成本組合 IP、帳號、Session、API Key、租戶、裝置、付款工具和全域容量，Token Bucket 可允許合理突發並限制長期速率。

回應 429 並提供適當 Retry-After，Client 使用抖動退避，避免同時重試形成雪崩。高風險功能除了每秒速率，還需要每日總額、同時工作、儲存與金額配額。限速儲存本身要有容量與失效設計，系統也要決定 Limit Service 故障時哪些低風險路徑可 Fail-open、哪些敏感路徑必須 Fail-closed。

GLOBAL整體容量

保留核心路徑空間，超載時啟動降級

TENANT租戶預算

避免單一客戶耗盡共享 DB、Queue 或第三方額度

IDENTITY帳號／Key／裝置

跨 IP 聚合操作與每日配額

ENDPOINT成本權重

匯出、搜尋、登入、寄信依實際成本計價

圖 4｜公平而非只封鎖 限速同時保護整體容量與單一使用者公平，維度依業務風險組合。

05

ABSORB WITHOUT HIDING FAILURE

吸收尖峰必須有界線，否則只是延後崩潰

Cache 降低重複計算與資料庫壓力，但 Key 必須包含所有影響內容與授權的維度，私有資料不進共享 Cache，TTL、失效與 Stampede 保護明確。對熱門公開內容可在 CDN 提供 Stale-while-revalidate；對核心動態資料則寧可回受控舊值，也不要把錯誤無限快取。

Queue 將昂貴工作移出 Request Path，卻需要最大深度、每租戶配額、訊息大小、Retry 上限、Dead-letter 與過期。Backpressure 表示下游飽和時上游減速或拒絕，不繼續接受無限工作。監控 Queue Age 比只看 Queue Length 更能反映使用者等待時間；Consumer 要冪等，避免重試放大成本。

CACHE減少重複工作

正確 Key、TTL、失效、私有資料隔離與 Stampede 控制

QUEUE有限等待

最大深度、每租戶額度、過期、DLQ 與可見狀態

WORKER受控並行

Deadline、資源 Pool、冪等、Retry Budget

BACKPRESSURE明確減速或拒絕

下游飽和時保護核心服務與資料一致性

圖 5｜吸收尖峰但不隱藏過載 Cache 和 Queue 都必須有容量、失效與拒絕策略，才能保護下游而不是累積債務。

06

PROTECT THE BUSINESS RULE

辨識自動化只是手段，真正要守的是稀缺資源與公平性

Bot 可能是搜尋引擎、合作整合、輔助工具，也可能大量註冊、爬取、搶占庫存、寄送垃圾訊息或測試憑證。不要把「不是人類」直接等同惡意；先定義哪些行為、速度、資源占用或業務結果不可接受，再選擇認證 API、配額、排隊、公平分配與必要的人機挑戰。

CAPTCHA 會增加真實使用者障礙，也可能被繞過，不應成為唯一控制。可使用已驗證帳號年齡、付款工具、裝置連續性、行為速率、庫存保留與風險式 Step-up 組合判斷，但要考慮隱私、無障礙與誤判申訴。所有自動封鎖都有期限、理由碼和人工解除流程。

PARTNER認證 API

專用 Key、Scope、Quota、Version 與聯絡人

PUBLIC公開內容

Cache、合理 Crawl Policy、速率與資料最小化

ACCOUNT功能濫用

信箱、寄信、優惠、儲存與匯出按帳號配額

SCARCE稀缺資源

排隊、公平分配、持有期限、Step-up 與申訴

圖 6｜先保護業務資源 產品規則、認證與配額通常比單純猜測是不是 Bot 更可解釋。

07

FAIL GRACEFULLY

過載時主動捨棄次要功能，比全部一起失效更安全

依業務優先級定義降級層級：關閉即時推薦與大型匯出、降低圖片品質、延長非關鍵同步、將寫入排隊、對公開內容提供 Stale Cache，同時保留登入、核心讀取、付款確認與資料完整性。Bulkhead 把 Worker、Connection Pool 與 Queue 依功能隔離，避免次要功能耗盡共同資源。

Circuit Breaker 在第三方失敗達門檻時暫停呼叫，避免每個 Request 都等待 Timeout；恢復時逐步放量並驗證依賴。Autoscaling 有幫助但不是安全控制：它可能放大成本或來不及追上攻擊。設定最大規模與 Budget Alert，並確保資料庫、Queue 與第三方容量能配合。

NORMAL完整功能

觀察基準、預熱 Cache、保留容量與定期演練

LIMIT提高保護

降低非關鍵配額、收緊昂貴 Endpoint 與重試

DEGRADE保住核心任務

停用次要功能、Stale Read、Queue Write、隔離 Pool

RECOVER逐步放量

驗證依賴、清理 Queue、恢復 SLO 並回顧成本

圖 7｜有設計的過載狀態 預先決定哪些功能先捨棄、誰能啟動、如何恢復，事件時才不會臨場猜測。

08

PREPARE BEFORE THE SPIKE

真正的大流量事件，需要平台、供應商與產品一起處理

Runbook 記錄關鍵任務與 SLO、正常基準、Edge／CDN／ISP 聯絡方式、Dashboard、告警、各限速規則 Owner、降級開關、全域與功能容量、雲端預算、資料庫保護、溝通模板與停止條件。容量型 DDoS 超出 Origin 能力時，必須由上游 Edge 或清洗服務吸收，不能等流量到主機才處理。

演練使用桌上推演或隔離測試，不在正式環境製造攻擊流量。從『登入失敗暴增』『匯出 Queue 積壓』『第三方 Timeout』『頻寬飽和』等情境走過判斷、限速、降級、溝通與復原。事件後分開分析惡意流量、合法尖峰與系統設計缺口，避免只新增永久封鎖規則。

DETECT確認瓶頸

SLO、流量、成本、Queue、DB、依賴與地理分布

PROTECTEdge 與限速

上游吸收、多維配額、核心路徑保留

DEGRADE捨棄次要功能

Feature Flag、Bulkhead、Cache、Queue 與 Circuit Breaker

RECOVER逐步回復

清理積壓、驗證一致性、供應商對帳與事後改善

圖 8｜可用性事件 Runbook 平台、應用、資料與產品控制要能在同一事件中協調，而不是各看各的 CPU。

FIELD ASSIGNMENT

用 45 分鐘完成可用性預算與 Runbook

只分析既有 Metrics 或估算值；不要對正式站產生壓力流量。

  1. 00–10

    選三個關鍵任務為登入、核心讀取與寫入定義成功率、P95／P99、成本與可接受降級。

  2. 10–22

    列昂貴 Endpoint記錄最大 Input、DB、第三方、CPU、Bytes、Timeout、Queue 與每租戶成本。

  3. 22–33

    設計多層控制安排 Edge、全域、租戶、帳號與 Endpoint 限速，以及 Cache、Queue、Backpressure。

  4. 33–45

    寫事件 Runbook加入聯絡人、Dashboard、降級開關、供應商、預算、恢復條件與溝通模板。

CHECK YOUR MODEL

先回答，再展開。

網站回 200 是否代表可用性正常？

不一定。關鍵任務可能超時、錯誤或成本失控，需看成功率、延遲、正確性與使用者結果。

只依 IP 限速公平嗎？

通常不夠。共用網路與分散式 Bot 需要結合帳號、Session、Key、租戶、裝置與功能成本。

Queue 可以無限吸收尖峰嗎？

不能。Queue 需要最大深度、配額、過期、Retry Budget、DLQ 與 Backpressure。

Autoscaling 能單獨解決 DDoS 嗎？

不能。可能追不上流量、壓垮資料庫或放大成本，仍需 Edge、限速、資源上限與降級。

CAPTCHA 是否等於 Bot 防禦？

不是。它只是訊號或摩擦之一，仍需認證、配額、產品公平規則、監控與申訴。

保護可用性，就是保護關鍵任務與成本邊界。

01

以關鍵任務的成功率、延遲、成本與復原定義可用性，不只看主機在線。

02

03
