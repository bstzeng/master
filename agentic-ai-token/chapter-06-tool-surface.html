COURSE OUTLINE / CHAPTER 06

EXPOSE THE SMALLEST TOOLSET

只給 Agent 真正需要的工具

每個工具都帶來描述、Schema、路由選擇與錯誤處理成本。工具面越大，Agent 越可能選錯、問更多或攜帶無關說明；高效率設計從最小可用工具集開始。

70–90 分鐘8 個完整段落實例＋模板＋作業品質優先

LEARNING OUTCOME

完成本章後，你能建立工具 Inventory，按任務動態暴露工具，撰寫精簡且可預測的工具契約，並以權限、錯誤與路由 Eval 驗證工具面。

IMPORTANT BOUNDARY

縮小工具不是繞過權限。任何外部寫入、付費、刪除或不可逆操作仍需清楚授權、最小權限與稽核；不要用一個『萬能工具』藏住高風險副作用。

01

COUNT THE TOOL SURFACE

未使用的工具不只占 Token，也擴大選擇空間

工具名稱、說明、參數 Schema、欄位描述與錯誤行為通常會進入模型可見內容。一次暴露數十個工具，即使最後只用一個，也增加每回合前綴與路由難度。功能相似或名稱含糊時，選錯與重試也會上升。

先建立 Tool Inventory：任務類型、用途、讀寫性、副作用、輸入、輸出大小、錯誤、重試安全、所需權限與使用頻率。標記重複工具、很少使用工具與只在特定流程需要的工具，作為縮小工具面的依據。

ERROR重試成本

輸出不清會再呼叫或改用錯工具

RISK副作用與權限

02

ROUTE BEFORE EXPOSURE

先判斷工作類型，再提供小型工具包

程式修改需要搜尋、讀檔、Patch與測試；研究任務需要搜尋、開頁與引用；資料分析需要查詢、過濾與計算。先用輕量路由或應用邏輯選出工具包，避免所有任務看見所有能力。

路由失敗要有保守退路：缺少必要工具時回傳明確缺口或允許一次受控升級，而不是暴露整個工具目錄。工具搜尋或延遲載入適合大型生態，但搜尋本身也有成本，應對高頻路徑保留直接工具組。

EXECUTE使用局部契約

模型只在少量選項中決定

ESCALATE缺工具才擴張

一次受控載入並留下理由

03

DESCRIBE FOR DECISION

說明何時用、輸入什麼、會發生什麼與如何失敗

好描述不需要行銷語，而要讓模型作路由決策：工具解決的問題、何時不該用、必填輸入、輸出欄位、副作用、是否可安全重試，以及常見錯誤。名稱使用具體動詞與物件，避免 generic_action、helper 或 manage。

參數只保留執行需要的欄位，能由伺服器推導的值不要讓模型重複生成；使用 Enum、型別與界限取代長篇自然語言。回傳狀態固定，錯誤包含 category、retryable、message 與必要 context，讓 Agent 不必猜測下一步。

{
  "ok": false,
  "error": {"category": "transient", "retryable": true},
  "summary": "上游暫時無法使用",
  "next_allowed_action": "retry_once"
}
WHEN使用條件

解決什麼問題，何時不適用

INPUT最小參數

必填、型別、界限與可推導欄位

EFFECT副作用

讀取、寫入、付費、通知或不可逆

ERROR固定錯誤契約

類型、可重試、訊息與缺少內容

04

ONE RESPONSIBILITY PER TOOL

工具過大會讓權限、輸出與重試行為難以推理

一個工具同時查詢、修改、發布與通知，模型很難預測副作用，也無法只取得讀取權限。反過來，十個工具只差一個欄位，也會讓路由選擇膨脹。合理粒度是每個工具有清楚責任與一致風險等級。

將讀取與寫入分開，預覽與提交分開，高風險動作提供 dry-run 或 plan token。功能相同但資料源不同，可用受控 source Enum 合併；輸入、權限與錯誤完全不同的工具則保持獨立。設計依據是決策邊界，不是追求工具數最少。

READ讀取工具

無副作用、可直接重試、輸出可限制

PREVIEW預覽變更

回傳差異、成本與影響，不提交

WRITE明確提交

需要授權、冪等鍵與稽核

NOTIFY外部訊息

內容、對象與確認邊界獨立

05

ENFORCE CAPABILITY

Prompt 說『不要做』不能取代真正的工具限制

Token 精簡常想刪掉重複安全提醒，前提是後端有真實控制：工具憑證最小權限、允許的資源與操作被系統限制、重要寫入需要確認或一次性 capability。這樣安全不依賴每回合重複幾百字警告。

工具回傳應指出已核准範圍與 remaining capability，Agent 不需反覆詢問。對外部與昂貴操作，在執行前回傳預覽供使用者確認；確認後只允許提交同一份已核准內容，避免第二次解析產生漂移。

PROMPT說明政策

幫助模型選擇，但不是唯一防線

CREDENTIAL最小權限

工具只能接觸必要資源與動作

PREVIEW固定即將執行內容

對象、變更、費用與風險

CAPABILITY一次性授權

只提交已確認內容並留下稽核

圖解｜把權限放在系統而不是提示 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

06

OPTIMIZE THE COMMON PATH

每次都搜尋工具目錄，可能比固定小工具組更貴

工具搜尋適合工具很多且任務多變的系統，但高頻、穩定流程可直接載入 3–6 個工具。先觀察任務分布：80% 流量是否集中在少數工具包？若是，建立快捷路由；長尾才使用工具搜尋。

路由層也要評測錯選、漏選、升級與 Token。若工具搜尋回傳冗長描述，先只回名稱、用途摘要與風險，選中後再載入完整 Schema。這與文件檢索的粗到細策略相同。

FAST PATH高頻固定工具包

無搜尋成本，路由清楚

SEARCH長尾工具探索

先取 Metadata，不載完整 Schema

LOAD選中後載入

只加入真正要用的工具契約

FALLBACK明確缺口

找不到時停止或受控擴張

07

EVALUATE THE CHOICE

工具本身能用，不代表 Agent 會選對

為每個工具建立正例、近似工具反例、不應用工具的任務、缺參數、權限不足、暫時錯誤與不可重試錯誤。評分包括是否選對、參數是否正確、是否多呼叫、是否錯誤重試與最終任務是否成功。

特別觀察『零工具』案例。模型若能直接回答，卻先呼叫工具取得不必要資料，就增加 Token 與延遲。路由 Eval 應允許正確答案是不用工具，並對重複呼叫相同查詢設成本。

POSITIVE該用哪一個

選擇、參數與必要證據

NEGATIVE不該使用

模型已具足夠資訊或工具有副作用

NEAR MISS相似工具

檢查描述能否區分邊界

ERROR失敗後決策

重試、換路徑、詢問或停止

圖解｜測試路由而非只測工具 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

08

SHIP THE TOOLSET

把工具、路由、權限與輸出成本放在同一張圖

完成品包括 Inventory、任務到工具包的路由表、每個工具的精簡契約、權限與錯誤分類，以及 15–30 個路由 Eval。再標記高頻快捷路徑和長尾搜尋路徑。

比較 All-tools 與 Routed-tools 兩個版本：輸入 Token、選錯率、工具呼叫數、重試與成功率。只有工具縮小後仍能處理缺工具與高風險動作，才是可部署設計。

CHECK YOUR MODEL

先回答，再展開。

工具越少一定越好嗎？

不是。目標是最小可完成集合；缺少必要工具會增加失敗與升級。

為什麼工具描述不能只寫功能名稱？

模型需要使用與不使用條件、輸入、輸出、副作用和錯誤，才能正確路由。

安全提醒寫在 Prompt 就夠嗎？

不夠。必須以憑證、資源範圍、確認與一次性能力在系統層強制限制。

什麼時候需要工具搜尋？

工具生態大、任務長尾多時；高頻穩定路徑通常使用固定小工具包更有效率。

如何測工具路由？

同時測該用、不該用、相似工具、缺參數、權限與不同錯誤，並計算多餘呼叫。
