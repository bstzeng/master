MAKE REPETITION CHEAPER

Prompt Cache 與可重複內容

Prompt Cache能讓重複前綴更便宜，但前提是內容穩定、排列一致、重複量足夠，而且你真的觀察到命中。快取是優化層，不是上下文垃圾桶。

70–95 分鐘8 個完整段落實例＋模板＋作業品質優先

LEARNING OUTCOME

完成本章後，你能將穩定前綴與動態尾端分離，管理版本與失效，量測命中、寫入與讀取，並判斷快取的淨節省是否值得。

IMPORTANT BOUNDARY

快取行為、門檻、費率與保存時間依平台與模型而異。不要依課程假設固定價格；請使用當前官方文件和 Usage欄位驗證。敏感資料仍依資料政策處理。

01

REUSE A COMMON PREFIX

重複內容可能降價與降延遲，但仍占邏輯上下文

Prompt Cache辨識請求開頭相同的內容，讓後續相似請求重用。它最適合大量請求共享長而穩定的系統規則、工具定義或參考前綴。若每次內容都不同或只執行一次，命中價值有限。

快取不是回覆快取：動態使用者資料仍由模型處理；也不是品質優化：不相關前綴即使命中，仍會占模型上下文並可能干擾。先完成提示與工具瘦身，再對真正需要的重複內容做排列。

PREFIX相同開頭

穩定規則、工具與共享參考

DYNAMIC變動尾端

本次目標、使用者資料與即時結果

HIT重用既有前綴

觀察 cached usage，不靠猜測

LIMIT不改善相關性

快取不能讓無關內容變成好Context

02

ORDER FOR MATCHING

小變動插在前綴中間，可能讓後面全部無法重用

將平台政策、核心任務契約、穩定工具 Schema與版本化參考放在前面；租戶、使用者、時間、查詢、檔案片段與工具結果放後面。避免在穩定區加入當前日期、隨機 ID或每次不同的排序。

一致的序列化也重要：JSON欄位順序、空白、工具順序與版本字串若隨機變化，語意相同也可能無法匹配。建構 Prompt時使用確定性模板，並把變動 Metadata集中到動態段落。

[穩定] 系統政策 → 任務型規則 → 工具 Schema → 共享參考
[動態] 租戶／使用者 → 本次目標 → 檢索片段 → 工具結果

少量、版本化、所有請求確實需要

TOOLS穩定工具組

高頻路徑工具順序與Schema一致

ROUTED任務型前綴

不同工具包建立不同可重用前綴

03

CALCULATE REUSE

前綴很長但流量很低，未必值得特別設計

估算相同前綴的請求量、前綴大小、命中率、快取寫入與讀取成本、保存時間與版本變更頻率。淨節省取決於有多少後續請求真的在有效期內重用，而不是只看單次命中折扣。

建立 Break-even模型：首次建立與維護成本，何時由後續讀取節省抵銷。若前綴每十分鐘改版、任務很分散或每個租戶都有獨特內容，可能先做上下文縮減與路由更有效。

淨節省 ≈ 未快取成本
-（快取寫入 + 快取讀取 + Miss + 維護成本）

只有真正需要且穩定的內容

VOLUME重複請求量

相同版本在有效期內會出現幾次

HIT RATE實際命中比例

由Usage量測，依路由與版本分組

不要只看讀取折扣，需算淨值

04

VERSION THE PREFIX

前綴改動會影響行為與快取，不能偷偷漂移

為System Prompt、工具包與參考前綴建立版本 ID；變更時記錄原因、Eval與生效時間。安全政策、工具 Schema或產品規則更新必須立即切換新版本，不為維持命中而使用過期內容。

避免所有任務共享單一巨大前綴，因為任何小改都使整體失效。依穩定邊界分成少數路由前綴，例如研究、程式與資料；每個前綴只包含該路由通用內容。版本過多又會稀釋流量，需要在相關性與命中間平衡。

提示、工具、參考與變更理由

INVALIDATE安全與Schema更新

正確性優先，不保留過期命中

ROUTE少數任務型前綴

避免一個全能前綴或無數微版本

EVAL版本切換前驗證

品質、命中、成本與回復

05

MEASURE THE CACHE

沒有 Usage細節，就不能宣稱快取省了多少

Dashboard按模型、前綴版本、路由與時間記錄總輸入、cached tokens、cache write tokens、Miss、命中率、請求量與P50/P95延遲。若平台欄位不同，使用其官方定義，不自行混算。

命中率突然下降可能來自模板變動、工具順序、租戶資料插入前綴、版本發布或流量分布改變。建立變更註記，讓曲線能對應部署。只報高命中也不夠，還要看每成功任務成本與品質。

OUTCOME仍看成功任務

06

KEEP TENANT DATA DYNAMIC

共享前綴不能混入不應共享或頻繁變動的資料

將租戶設定、使用者內容、權限與私有文件放在動態區，並遵守平台資料政策。即使技術上能使用快取，也不代表應把敏感資料設計成跨請求共用前綴。

可共享的是通用政策與公共參考；租戶專屬規則可建立受控、隔離且有版本的前綴，但必須評估請求量是否足夠，以及存取和到期是否符合要求。快取鍵與日誌避免直接使用可識別個資。

07

DON'T OPTIMIZE THE WRONG THING

為快取把無關內容塞進前綴，是用低單價購買更多噪音

反模式包括：一個超大通用前綴給所有任務、每次插入日期導致Miss、隨機工具順序、為了命中延遲安全更新、只報cached tokens不算寫入與失敗，以及把最終回答快取和Prompt Cache混為一談。

修正順序固定：先刪無關內容，再按任務路由，穩定模板與排序，最後才觀察快取。若相同輸入應產生可直接重用的結果，可另評估應用層 Response Cache，但必須處理資料新鮮度、權限與個人化。

命中不代表相關，先縮小與路由

DRIFT動態值插入前段

日期、ID、排序與序列化要穩定

STALE為命中保留過期內容

安全與正確性永遠優先

MIXUPPrompt與Response Cache

兩者解決不同問題，風險與失效也不同

08

PROVE NET SAVINGS

用真實重複流量比較重排前後，而不是只做一次請求

選一個高頻且共享前綴長的路由，建立 Baseline與Cache-friendly版本。固定內容相同、動態資料移到後端、序列化穩定，連續執行能代表真實重用的請求序列。

比較品質、總輸入、cached、write、Miss、延遲與每成功任務成本；同時模擬版本更新與安全規則變更，確認能正確失效。最後寫下 Break-even、適用流量、版本策略與監控告警。

CHECK YOUR MODEL

先回答，再展開。

Prompt Cache會降低模型看見的上下文嗎？

不會。它改變重複前綴的處理成本與延遲；內容仍在邏輯上下文中。

穩定內容是否都應放進前綴？

不是。先確認對該路由相關且必要，再考慮穩定與快取。

為什麼只看命中率不夠？

還需計算寫入、Miss、前綴大小、品質、請求量與每成功任務成本。

安全規則更新時應維持舊前綴嗎？

不應。正確性與安全優先，立即切換版本並讓舊內容失效。

Prompt Cache等於Response Cache嗎？

不是。前者重用輸入前綴處理，後者直接重用結果，失效與資料風險不同。
