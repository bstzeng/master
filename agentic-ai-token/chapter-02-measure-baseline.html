COURSE OUTLINE / CHAPTER 02

COST PER SUCCESSFUL TASK

先量測，再開始節省

Token 變少不等於系統變好。你需要的是一組固定任務、一個可判斷的成功標準，以及能同時看品質、成本與延遲的 Scorecard。

70–90 分鐘8 個完整段落實例＋模板＋作業品質優先

LEARNING OUTCOME

完成本章後，你能建立 10–30 個代表性任務，計算每個成功任務的總成本，設計品質閘門與 Token 預算，並用 A/B 基準避免『省了 Token，卻多了重做』。

IMPORTANT BOUNDARY

任何百分比都只對測試樣本有效。不要把單一成功案例當成普遍結論；先固定模型、提示、工具版本與資料集，再比較一項改動。

01

QUALITY BEFORE SAVINGS

沒有成功標準，省下的 Token 沒有意義

對問答任務，成功可能是必要事實、來源與限制都完整；對程式任務，成功可能是測試通過且沒有新增回歸；對研究 Agent，成功可能是找到指定證據並正確引用。先把成功拆成可觀察條件，才能知道精簡後是否仍合格。

避免用『感覺不錯』作評分。建立 Must-have 與 Nice-to-have：前者缺一就失敗，後者用來比較品質。省 Token 實驗只在 Must-have 全部通過時成立；如果成功率下降，就把失敗重跑的成本算回總帳。

MUST必要完成條件

正確答案、必要證據、格式與安全限制

NICE品質加分

可讀性、延伸背景與更佳說明

FAIL明確失敗

缺欄位、錯事實、工具未完成或測試未過

REWORK重做也算成本

人工修正、重跑與升級模型全部加入總帳

圖解｜定義真正的成功 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

02

BUILD THE EVAL SET

測你真的會做的工作，不要只測最漂亮的範例

任務集要覆蓋常見、困難、長上下文、工具失敗、模糊需求與邊界案例。若只挑提示詞原本就能處理的簡單題，精簡後看起來一定很好；一遇到真實專案與不乾淨資料就可能崩潰。

先從 10–30 個任務開始，每個任務固定輸入、預期證據、評分方式與允許變動。敏感資料以合成或匿名案例替換。日後每次發生高成本或品質事故，就把該案例整理成新的回歸任務。

COMMON高頻任務

最常消耗總預算的日常工作

HARD高難任務

需要多步推理、工具與長上下文

EDGE邊界案例

缺資料、衝突、工具錯誤與權限限制

INCIDENT真實失敗

把成本尖峰與品質事故變成回歸測試

圖解｜建立代表性任務集 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

03

OBSERVE EACH RUN

沒有階段標籤，總 Token 很難轉成行動

每次 Run 產生唯一 ID，記錄任務類型、模型、版本、推理設定、提示版本、工具組、開始與結束時間、各回合 Token、快取細節、工具呼叫、錯誤、重試與結果評分。至少能從任務總額鑽到最貴的回合。

若平台只提供總 Usage，就在應用層替每次呼叫加上 stage、agent、tool 與attempt標籤。內容本身不一定保存，尤其含敏感資料時；可保留雜湊、長度、來源類型與必要診斷欄位。可觀測性不等於把所有 Prompt 永久寫進日誌。

run_id, task_type, prompt_version, model, stage
input_tokens, output_tokens, cached_tokens, reasoning_tokens
tool_calls, retries, latency_ms, success, quality_score
RUN完整任務

任務類型、版本、開始、結束與結果

CALL單次模型呼叫

階段、模型、Token、快取與延遲

TOOL外部操作

工具、輸入摘要、結果大小、狀態與重試

PRIVACY最小化日誌

保留診斷資料，不無限保存敏感內容

04

NORMALIZE THE COST

平均每次呼叫便宜，可能只是把失敗藏到下一次

核心指標是 Cost per Successful Task：所有首次嘗試、重試、模型升級、工具與人工修正的總成本，除以成功完成數。如果精簡提示讓單次成本下降 30%，卻讓 20% 任務需要重跑，實際節省可能消失。

同時保留 P50 與 P95。平均值會被少數大型任務拉動，而 P95 能揭露長尾尖峰；再按任務類型分組，避免短分類任務掩蓋長研究任務。Token、金額與延遲都要看，但不要把不同模型單價直接當成能力比較。

每成功任務成本 =（首次 + 重試 + 升級 + 工具 + 人工）總成本 ÷ 成功數
TOTAL所有嘗試總成本

首次、重試、升級、工具與人工處理

SUCCESS成功任務數

必須通過固定 Must-have 閘門

P50典型成本

多數使用者平常會感受到的水準

P95長尾成本

找出 runaway loop、超大輸入與工具尖峰

圖解｜成本要除以成功任務 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

05

BUDGET THE RUN

不要只設一個總上限，否則不知道哪一步先失控

將任務分成理解、檢索、執行、驗證與輸出。每一階段都有 Token、呼叫、工具、時間與重試預算；預算不是一定用完的配額，而是超過時必須切換策略或回報的界線。

例如檢索階段超過預算時，先收斂查詢與 Top-K，而不是繼續塞文件；執行階段接近上限時，停止探索新方案，轉入完成與驗證；驗證失敗時只允許一次有新證據的修正。這些規則讓 Agent 在便宜路徑失敗得清楚，而不是昂貴地迷路。

UNDERSTAND任務契約

一次釐清目標與成功條件

RETRIEVE證據預算

限制查詢、Top-K 與載入片段

EXECUTE行動預算

工具、檔案與修改範圍

VERIFY驗證預算

測試、證據與有限修正

06

CHANGE ONE VARIABLE

提示、模型、工具與資料一起改，結果就無法解釋

建立 Baseline A，複製相同任務集形成 Variant B，一次只改一個主要變因，例如刪除一組範例、降低 Top-K、縮小工具輸出或調低推理強度。固定可固定的模型版本、工具資料與執行環境，重複數次降低偶然性。

比較 Must-have 通過率、品質分數、總 Token、每成功任務成本、延遲、呼叫、重試與人工介入。先看品質是否仍達門檻，再看成本改善；若某些任務受損，可能需要條件式路由，而不是把整體改回最昂貴設定。

BASELINE原本可用版本

固定提示、模型、工具與資料

VARIANT只改一項

讓差異可以被解釋

GATE先過品質

Must-have 通過才計算節省

SEGMENT按任務分流

不是每一類都用同一個設定

07

DON'T GAME THE METRIC

省 Token 指標也會被錯誤目標帶偏

若只獎勵 Token 少，Agent 可能少做驗證、過早停止或省略必要證據；若只獎勵成功率，Agent 可能使用最強模型、重試到成功。Scorecard 必須同時包含品質、成本、延遲與操作限制，才能形成合理取捨。

另一个陷阱是拿不同難度期間互比。例如本月任務更複雜，平均 Token 上升不代表系統退步。使用固定 Eval Set 做版本比較，再用正式流量監控真實分布；兩者互補，不能互相取代。

TOKEN ONLY過早停止

少驗證、少證據，看似便宜但不可靠

QUALITY ONLY無上限探索

重試與最高設定把成本推高

FIXED EVAL比較版本

控制任務難度，判斷改動效果

LIVE TRAFFIC看真實分布

監控新任務、尖峰與使用者行為

圖解｜避免常見量測陷阱 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

08

MAKE IT OPERATIONAL

每一項節省都要能被重跑、解釋與回復

Scorecard 至少要有：任務集版本、提示與工具版本、Must-have 通過率、品質分數、輸入／輸出／快取／推理 Token、工具成本、P50／P95 延遲、重試、人工介入與每成功任務成本。再補上變更說明與是否採用。

設定採用規則，例如：Must-have 不下降超過容許範圍、關鍵任務零回歸、每成功任務成本至少改善 15%，P95 延遲不惡化。數字不是通用標準，而是強迫團隊先說清楚何謂值得。

QUALITY任務仍正確

Must-have、分數與關鍵任務回歸

COST總帳真的下降

所有嘗試與工具納入每成功任務成本

LATENCY使用體驗可接受

P50、P95 與 Timeout

DECISION採用或回復

版本、理由、風險與下一個實驗

BEFORE / AFTER

單次省 28%，為什麼每成功任務只省 6%？

WASTEFUL

Baseline 單次平均 10 單位，成功率 95%。

OPTIMIZED

Variant 單次平均 7.2 單位，但成功率降到 78%，且部分失敗需要高成本重跑。

WHY IT WORKS

把失敗重跑算回來後，淨節省只剩少量；應只對穩定任務使用 Variant，困難任務保留 Baseline。

CHECK YOUR MODEL

先回答，再展開。

為什麼不能只比較平均 Token？

平均值不含成功率與長尾；應看每成功任務成本，以及 P50、P95 和重試。

任務集應該全是困難題嗎？

不應。需要反映真實分布，同時包含高頻、困難、邊界與已發生的失敗。

A/B 可以同時換模型和改提示嗎？

可以做產品比較，但難以知道原因；優化實驗最好一次只改一個主要變因。

為什麼正式流量不能取代固定 Eval Set？

正式任務難度會變，無法穩定比較版本；固定集控制難度，正式流量則補充真實分布。

Token 預算到了就直接截斷嗎？

不一定。更好的策略是切換檢索、停止探索、降級輸出或返回結構化缺口，避免產生不完整假成功。
