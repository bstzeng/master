01

ARCHITECT THE SYSTEM

Token效率不是某一條Prompt，而是端到端架構

完整流程包括入口分類、任務契約、上下文檢索、工具路由、模型路由、狀態與記憶、執行迴圈、驗證、最終輸出與觀測。每一層都可能放大或抑制 Token。

把控制面與工作面分開：控制面設定預算、權限、版本、路由與告警；工作面執行模型與工具。當成本異常，控制面可停止、降級或切換路徑，而不用改寫每個 Prompt。

02

ALLOCATE BEFORE RUNNING

總上限之外，還要知道哪一步可以讓、哪一步不能讓

建立Task Budget Envelope：總Token、金額、時間、工具呼叫、外部費用與最大Agent數；再分配給理解、檢索、執行、驗證與輸出。保留少量Recovery Reserve，只在有新證據的修正時使用。

預算依任務級別不同：Routine緊、High-risk可多花驗證但不能無上限；研究任務給證據預算，寫作任務給輸出預算。若某階段常超支，先改該層設計，不直接提高全部上限。

總 Budget = Input + Output + Reasoning + Tools + Retry Reserve
硬優先：安全／授權 → 正確性／證據 → 完成核心 → 可選詳細度
UNDERSTAND契約預算

釐清目標與硬限制，不反覆追問

RETRIEVE證據預算

查詢、Top-K、片段與Artifact

EXECUTE行動預算

模型、工具、Agent與重試

VERIFY品質預算

測試與證據不可被可選文案擠掉

03

BALANCE FOUR OUTCOMES

品質、成本、延遲與安全必須一起監控

SLO可以包含Must-have通過率、每成功任務成本、P95延遲、人工介入率、重試率與安全事件。Guardrail則是不可突破的界線，例如關鍵任務成功率、外部寫入核准、最大費用與敏感資料政策。

不同任務類型有不同門檻，避免用全站平均掩蓋高風險流量。Dashboard先以task_type、route、model、prompt_version、tool_bundle與agent_count切分；再看趨勢和長尾。

04

DEGRADE GRACEFULLY

預算不足時先減少可選內容，不要偷掉必要工作

降級順序依任務設計：先降低可選詳細度與延伸背景，再縮小非必要檢索範圍、關閉額外獨立檢查、選擇較低推理或模型；若必要證據仍不足，回傳partial與缺口。

高風險驗證、安全規則、授權與資料治理不可降級。若使用較低模型導致Must-have不過，路由應升級或失敗，而不是輸出無證據成功。降級動作要在Trace中可見，使用者必要時知道結果範圍較窄。

TRIM可選輸出

NARROW非必要範圍

Top-K、額外來源與獨立檢查

ROUTE較低成本設定

只有通過該類任務Eval才使用

STOP保留誠實缺口

必要證據不足就partial，不假成功

05

ALERT ON RUNAWAY BEHAVIOR

突然變貴通常有可觀察訊號，不必等帳單月底才知道

告警訊號包括：input_tokens或context growth異常、同工具重複、no-progress回合、重試率、升級率、多Agent fan-out、快取Miss、P95延遲與單任務費用超標。使用相對於task_type基準的異常，而不是一個全站固定值。

告警要附Run Trace、版本、最貴回合、最大工具結果與最近部署。自動保護可停止低優先分支、禁止新fan-out、縮小輸出或保存Checkpoint後partial；對外部寫入不應因Timeout自動重播。

GROWTHContext異常成長

每回合輸入快速增加或重送比例升高

LOOP重複與無進展

相同工具、錯誤與狀態連續出現

ROUTE升級與Fan-out尖峰

昂貴路徑比例突然變化

PROTECT自動止損

保存狀態、停止低優先工作並清楚回報

06

LEARN FROM SPIKES

修掉一次尖峰，還要把案例變成回歸測試

事故流程：限制影響、保存Trace與Artifact、確認任務與版本、找出第一個異常回合、分類為Prompt、Context、Tool、Loop、Routing、Cache或Multi-agent，再修正控制並重跑固定案例。

Postmortem不只寫『Prompt太長』，而要找控制失效：為何沒有Budget、為何工具回傳無上限、為何Permission錯誤可重試、為何所有Agent讀相同背景。將事故加入Eval與告警，避免下次同類問題只換一個表面症狀。

CONTAIN先停止擴大

Run上限、Fan-out、重試與外部操作

TRACE保留證據

版本、回合、工具、Usage與Artifact

ROOT找第一個控制失效

不是只看最後最貴結果

PREVENT加入Eval與告警

修系統護欄，不只修單一Prompt

07

OPERATE THE FLYWHEEL

每週只改一個高影響假設，效果更容易累積

優化Backlog依影響×頻率×信心÷實作成本排序。每個項目寫假設、目標任務、改動、品質門檻、預期節省、觀測期與回復方式。一次只推進少量實驗，避免版本交錯無法解釋。

週節奏：檢查Top成本路由與事故、選一個熱點、跑離線Eval、灰度發布、觀察真實流量、採用或回復。月節奏：重新檢查模型與費率、清理工具與記憶、更新任務集與Budget。

RANK高影響Backlog

頻率、浪費乘數、信心與成本

EVAL離線固定任務

先確認品質與預期節省

CANARY小流量發布

比較真實分布與長尾

DECIDE採用或回復

記錄版本、證據與下一個實驗

CHECK YOUR MODEL

先回答，再展開。

正式環境只設總Token上限夠嗎？

不夠。需要按階段、工具、Agent與重試分配，才知道失控位置與降級策略。

預算不足時先省哪裡？

先減可選詳細度與非必要範圍；安全、授權、必要證據與核心驗證不可省。

哪些訊號代表Runaway Loop？

Context持續成長、重複工具、相同錯誤、無進展回合、重試與Fan-out異常。

為什麼成本事故要加入Eval？

將真實失敗變成回歸，確保修正控制後同類問題不再出現。

最終成功指標是總Token越低越好嗎？

不是。是品質與安全達標下，每成功任務成本和延遲更低、更穩定。
