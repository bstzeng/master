LOAD ONLY WHAT MATTERS

Context Engineering 上下文工程

Context Engineering 決定模型在這一刻看見什麼。做得好，Agent 用少量高相關證據完成任務；做不好，整個 Repository、長文件與舊對話一起進場，成本與錯誤同步上升。

85–110 分鐘8 個完整段落實例＋模板＋作業品質優先

LEARNING OUTCOME

完成本章後，你能設定 Context Budget，建立先定位、再局部讀取、必要時擴張的流程，並用相關性、權威性、新鮮度與去重控制程式、文件與檢索內容。

IMPORTANT BOUNDARY

內容少不代表資訊足夠。對法律、醫療、財務、安全與重大變更，必須保留必要證據、來源與不確定性；本章目標是選擇，不是任意截斷。

01

DESIGN THE WORKING SET

模型能看見，不代表模型需要看見

上下文包含系統提示、任務、歷史、工具定義、檔案、檢索片段與工具結果。窗口再大也不應視為免費倉庫；內容越多，成本越高，重點越容易被稀釋，互相衝突的舊資訊也更可能影響判斷。

把 Context 當成 CPU 的 Working Set：只放完成當前決策所需內容。原始資料留在 Repository、文件庫或 Artifact；模型需要時透過索引與工具局部取得。『全部載入比較安全』通常只是把選擇責任推給模型。

SYSTEM穩定規則

跨回合必要政策與任務契約

STATE當前狀態

已完成、決策、未完成與下一步

EVIDENCE當下必要證據

相關檔案片段、來源與工具結果

ARCHIVE外部完整資料

可檢索但不永久進入 Working Set

圖解｜Context 是工作記憶 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

02

SEARCH BEFORE READ

用檔名、符號、索引與關鍵字縮小範圍

對程式專案，先列目錄、搜尋符號與引用，再讀目標函式周邊；對長文件，先看目錄、摘要與段落索引，再開啟相關頁；對資料庫，先查欄位與條件，再回傳必要列。這種粗到細流程能把大量無關內容留在工具端。

每一步都要保留可回溯位置，例如檔案路徑、行號、章節、文件 ID 或查詢條件。若證據不足，擴張相鄰範圍或做第二次檢索，而不是一開始把全部送入。這是 Progressive Disclosure：先用低成本線索決定下一個讀取範圍。

1. 先列可能相關的檔案／章節，不讀全文
2. 搜尋目標符號與引用
3. 只讀命中周邊必要範圍
4. 證據不足時，說明缺口後再擴張
INDEX查看地圖

目錄、Schema、符號、標題與 Metadata

SEARCH縮小候選

關鍵字、引用、過濾條件與 Top-K

READ取得局部證據

目標段落加必要上下文

EXPAND不足才擴張

相鄰區塊、第二查詢或更高 Top-K

圖解｜先定位，再讀內容 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

03

RANK THE EVIDENCE

同時考慮權威、時間、範圍與重複

關鍵字相似不代表是正確來源。Context 選擇應評估：是否直接回答問題、是否為權威或原始資料、是否仍新鮮、是否適用當前版本與範圍、是否與已載入內容重複。舊規格與新程式碼衝突時，必須標示而不是混在一起。

建立簡單的 Context Score：相關性最高權重，其次是權威性與版本適配，最後扣除重複與噪音。分數不必由模型計算，可以在檢索層用 Metadata 過濾。對關鍵決策，保留少量互補來源，而不是十段內容相似的摘要。

RELEVANCE直接回答程度

是否支援當前判斷與所需欄位

AUTHORITY來源可信度

原始文件、正式設定、測試與程式碼

FRESHNESS版本與時間

是否適用目前模型、服務與分支

DIVERSITY互補而非重複

保留不同證據面，去除近似片段

圖解｜相關性不只看關鍵字 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

04

ALLOCATE CONTEXT

不是所有階段都需要完整背景

理解需求階段需要目標與限制；搜尋階段需要索引與查詢線索；實作階段需要目標檔案、介面與相鄰測試；驗證階段需要變更摘要、測試結果與錯誤。若每一階段都帶同樣全量背景，等於放棄階段化。

Context Budget 可以是 Token、片段數、檔案數或字元數。達到預算時先去重、摘要與排序，再決定是否增加；若增加，留下理由。預算不是硬截斷，而是觸發重新選擇的門檻。

Context Budget 範例
理解：目標 + 5 個硬限制
檢索：最多 8 個候選摘要
實作：最多 4 個完整局部片段
驗證：Diff + 相關測試 + 失敗摘要
UNDERSTAND目標與限制

低量但高權重的任務契約

RETRIEVE索引與候選

查詢線索、Metadata、Top-K

ACT局部實作證據

目標檔案、介面、相鄰測試

VERIFY變更與結果

Diff、測試、錯誤與驗收

圖解｜替每個階段設 Budget 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

05

ORDER FOR REUSE

固定前綴放前面，變動資料放後面

長期不變的核心政策、產品規格與工具契約適合形成穩定前綴；使用者本次輸入、即時檢索、時間與工具結果屬於動態內容。兩者混寫會讓每次小變動破壞可重用結構，也讓人難以維護。

將穩定內容版本化，變動內容以清楚邊界附加；如果某份規格只適用特定任務，就不要為了快取硬塞進所有請求。快取最佳化必須排在相關性之後：穩定但無關的前綴仍然是上下文負擔。

STABLE核心政策與契約

版本化、少變動、跨任務確實需要

ROUTED任務型參考

只有進入該路由時載入

DYNAMIC本次目標與狀態

靠近尾端，內容清楚分區

LIVE工具與檢索結果

最新、局部、可追溯，完成後可壓縮

圖解｜穩定與動態內容分離 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

06

CONTROL RETRIEVAL

Top-K 越大不代表答案越完整

RAG 常見浪費是每次固定回傳大量長片段，片段彼此重疊，甚至將整份文件不同切塊全塞進上下文。先用 Metadata 過濾產品、版本、日期與權限，再做相似度排序、去重與鄰接合併。

片段需要保留標題、來源、版本與定位，並限制每來源占比。若問題需要跨文件綜合，可先在檢索層聚合，再交給模型做語意判斷。對找不到證據的情況，回傳『缺少什麼』比用低相關片段填滿 Budget 更可靠。

FILTER先用 Metadata

產品、版本、日期、權限與類型

RANK相似度與權威

不只比對表面關鍵字

DEDUP合併重疊片段

同來源相鄰內容只保留一次

GAP證據不足要明說

不要用低相關內容填滿 Top-K

圖解｜檢索結果也要治理 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

07

RE-GROUND THE AGENT

長任務中要定期回到目標與當前證據

工作進行多輪後，Agent 可能被近期錯誤與工具輸出吸引，忘記最初目標。定期建立 Checkpoint：目標、硬限制、已決定、已完成、目前證據、未解問題、下一步。再用 Checkpoint 取代大段探索歷史。

重新定位不是把最初提示再次完整貼上，而是生成經驗證的短狀態。對重要限制可從權威來源重新讀取；對已完成事項只保留結果與驗證。這會在第五章進一步變成記憶與壓縮策略。

GOAL原始目的

一句話重申可驗收成果

DECISION已確定事項

附理由與來源，不重播所有討論

STATE已完成與未完成

目前 Artifact、測試與缺口

NEXT唯一下一步

避免同時開啟過多探索分支

08

SHIP THE CONTEXT PLAN

每份內容都要有進場理由與離場條件

Context Manifest 為任務列出來源、用途、最大範圍、載入時機、權威版本、去重方式與何時壓縮或移除。它讓上下文選擇從臨場直覺變成可檢查設計。

完成後，用一個長文件或大型 Repository 做比較：A 版全量載入，B 版先定位再局部讀取。比較總 Token、證據完整性、錯誤、呼叫與延遲。只有 B 版仍能引用必要證據，才算成功縮減。

SOURCE資料在哪裡

Repo、文件庫、資料庫、工具或記憶

WHEN何時載入

任務路由、階段與觸發條件

LIMIT最多載入多少

檔案、片段、欄位、Top-K 與 Token

EVICT何時離場

完成後摘要、外置或完全移除

圖解｜建立 Context Manifest 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

BEFORE / AFTER

整個 Repository 120k Token，任務只改一個驗證函式

WASTEFUL

一次載入所有檔案與 README，模型花大量上下文判斷哪些無關。

OPTIMIZED

先搜尋函式、呼叫點與測試，只讀 4 個局部片段；若介面不明再擴張到型別定義。

WHY IT WORKS

上下文大幅下降，且證據更聚焦；驗收仍要求相關測試通過。

FIELD ASSIGNMENT

完成一份 Context Manifest

挑一個至少 30 個檔案或 50 頁的真實資料源。

  1. 00–15

    列資料源與權威記錄版本、擁有者、定位方式與敏感性。

  2. 15–30

    設計粗到細流程定義索引、搜尋、局部讀取與擴張條件。

  3. 30–45

    設定 Budget限制候選、完整片段、每來源占比與歷史保留。

  4. 45–60

    跑 A/B 比較全量對選擇性載入，檢查證據與總 Token。

CHECK YOUR MODEL

先回答，再展開。

Context Window 很大，為什麼還要做選擇？

更大窗口不會消除輸入成本、重複與注意力稀釋；選擇能讓證據更相關且可追溯。

Top-K 設越大越安全嗎？

不一定。大量重複或低相關片段會增加成本與衝突；應先過濾、排序、去重，不足再擴張。

只看函式本身夠嗎？

視任務而定。通常還需介面、呼叫點與相關測試；流程是局部開始，證據不足再擴張。

快取是否應優先於相關性？

不應。穩定但無關內容仍會占窗口並干擾判斷；先決定內容是否需要，再優化排列。

Context Budget 達上限要直接截斷嗎？

先排序、去重、摘要與檢查缺口；需要擴張時留下理由，不應產生無證據的答案。
