COURSE OUTLINE / CHAPTER 03

SAY THE RIGHT THING ONCE

高效率提示詞設計

真正高效率的提示詞不是最短，而是每一句都有工作：說清楚結果、必要背景、硬限制、證據與完成條件，刪掉重複儀式和沒有測量價值的教條。

75–95 分鐘8 個完整段落實例＋模板＋作業品質優先

LEARNING OUTCOME

完成本章後，你能把冗長 System Prompt 拆成任務契約、全域政策、工具說明與動態資料，透過漸進刪減減少重複，同時穩定控制輸出長度與必要證據。

IMPORTANT BOUNDARY

不要把安全、法規、資料處理與不可逆操作邊界當成『冗字』刪除。精簡的原則是移除重複與無效內容，不是省略真正會改變行為的限制。

01

DEFINE THE OUTCOME

用五個欄位取代長篇角色扮演

高品質提示的骨架是：目標、相關背景、限制、必要證據、完成格式。這五項比『你是一位世界級專家、請深呼吸、逐步思考』更能穩定行為，因為它們直接定義任務與驗收。

先寫一版最小契約，再用 Eval 找缺口。目標描述使用者真正要拿到的成果；背景只放影響決策的資料；限制區分硬限制與偏好；證據說明要引用哪些檔案或測試；格式則約束最終交付，不規定模型每一步怎麼想。

目標：<可驗收成果>
背景：<只列影響決策的事實>
限制：<範圍／安全／相容性>
證據：<測試／來源／檢查>
輸出：<必要章節或結構>
GOAL要交付什麼

一句話描述可驗收結果

CONTEXT哪些事實會改變答案

只放相關資料與當前狀態

CONSTRAINT不能違反什麼

範圍、權限、安全與相容性

EVIDENCE如何證明完成

測試、引用、輸出欄位與驗收標準

圖解｜從任務契約開始 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

02

REMOVE DUPLICATION

重複不一定加強，反而可能製造衝突與確認迴圈

長提示常在開頭、工具說明、範例與結尾重複『先詢問』『不要修改』『要簡潔』。模型會花 Token 重新讀取，也可能因細微措辭差異不確定哪一條優先。把同一政策放在一個權威位置，其他地方只引用情境，不再改寫。

做去重時先把所有句子按意圖分組：權限、輸出、風格、工具、錯誤處理、驗證。每組保留最清楚且涵蓋完整的一段。若兩條看似相同卻有不同例外，先合併成條件式規則，不要直接刪除。

COLLECT按意圖分組

找出同義、近義與互相矛盾的規則

CANONICAL保留一個權威版本

完整寫出條件、動作與例外

DELETE移除其他改寫

不要在結尾再次提醒全部規則

TEST跑邊界任務

確認例外與安全行為沒有消失

圖解｜一條規則只說一次 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

03

KEEP GUIDANCE LOCAL

System Prompt 不該變成所有工具的完整操作手冊

工具的用途、何時使用、必填輸入、副作用、重試安全與錯誤欄位，應寫在工具定義附近；只有跨工具都成立的政策才留在全域提示。這樣沒有暴露某工具的任務，就不必攜帶它的整段說明。

將參考規範改成可搜尋的 Skill 或文件，讓 Agent 進入特定任務時再載入。範例也要有理由：保留能修正已測得錯誤或代表產品格式的例子；裝飾性、重複性範例先移除，因為它們會永久增加前綴。

SYSTEM跨工具政策

權限、資料處理、停止與最終驗證

TOOL工具局部契約

用途、輸入、輸出、副作用、錯誤

SKILL任務型知識

進入特定流程才完整讀取

EXAMPLE只保留有測量價值者

修正錯誤或鎖定必要產品格式

圖解｜把工具細節放回工具 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

04

PREFER OUTCOME OVER CEREMONY

過度流程指令會增加長度，也可能限制更好的路徑

對能力足夠的模型，逐條指定『先想十個方案、逐一分析、再自我批判三次』常會增加輸出與推理，卻未必改善結果。除非產品真的需要可稽核流程，否則應描述目標、風險與成功條件，讓模型選擇路徑。

需要固定流程時，也應把它寫成可檢查的階段與停止條件。例如資料遷移審查必須先確認備份、回滾與鎖表風險，這是業務要求；至於模型內部如何排列思考，不必要求逐字展示。把可觀察行為與不可觀察的思考儀式分開。

OUTCOME可驗收成果

要求結論、證據、風險與下一步

PROCESS必要業務階段

只有法規、審核或安全需要時固定

CEREMONY無證據的思考儀式

先刪除並用 Eval 驗證

STOP明確完成條件

通過驗收就停止，不繼續自我反思

圖解｜別規定模型每一步 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

05

BUDGET THE ANSWER

『簡潔』太模糊；告訴模型什麼必須保留、什麼先刪

輸出成本可以透過欄位、段落、字數與優先序控制。與其只說『短一點』，不如要求：先給結論，保留必要證據、重大限制與下一步；優先刪除開場、重複說明、泛用背景與禮貌收尾。

結構化輸出能減少反覆解釋 Schema 的提示與解析失敗，但不要把每個簡單回答都包成巨大 JSON。格式應服務下游：給人看的用短章節和表格；給程式的用嚴格欄位；同一份內容不要同時輸出散文、JSON 與重複摘要。

先給結論。保留必要證據、重大限制與下一步。
優先省略開場、重複、泛用背景與非必要延伸。
輸出：最多 5 點，每點 1–2 句。
KEEP結論與必要證據

任務完成所需的事實、限制與下一步

TRIM開場與重複

泛用背景、禮貌語、同義改寫優先刪

HUMAN人類閱讀格式

短章節、表格與清晰層級

MACHINE程式消費格式

只回傳需要的結構化欄位

06

ABLATE ONE BLOCK

從已經可用的 Prompt 開始，每次刪一組

直接把長提示重寫成極短版本，若品質變差很難知道缺了什麼。更可靠的方法是 Prompt Ablation：把內容分成規則、範例、工具、風格與背景區塊，一次移除一組，跑相同 Eval Set，通過就保留刪減。

記錄每次版本的 Token、成功率與哪個案例變差。若某個範例只修正少數任務，考慮條件式載入，而不是永久放回全域；若某條規則經多輪測試都不影響行為，移除它。Prompt 應像程式碼一樣版本化，而不是靠直覺越寫越長。

BASE已有可用版本

先保留成功基準與測試

REMOVE一次移除一組

規則、範例、工具或風格

EVAL重跑同一任務集

品質先過門檻，再比較成本

PROMOTE採用或回復

記錄版本、差異與受影響案例

07

COMPACT AUTONOMY

說清楚何時可以繼續，能減少無效確認回合

Agent 經常因『任何修改都先問』與『請主動完成』同時存在而停下。把權限分成讀取與診斷、範圍內可逆修改、外部寫入、破壞性操作與擴大範圍。前三者如何處理，用一段短政策講清楚。

有實質影響的模糊才詢問，例如會改變架構、對外發布或刪除資料；可以從檔案與測試確認的小問題，Agent 應先檢查再繼續。每少一次不必要確認，就少一次新回合及歷史重送，但安全邊界仍必須保留。

READ可直接檢查

檔案、日誌、文件與非破壞性診斷

LOCAL範圍內可逆修改

使用者已要求建置或修正時可進行

EXTERNAL需要確認

發布、訊息、付費、外部資料寫入

DESTRUCTIVE明確核准

刪除、覆寫、不可逆或重大擴張

08

SHIP THE PROMPT

能通過 Eval 的最短版本，才叫有效精簡

完成品包含一份 Base 與 Lean 版本，附 Token 差異、刪除區塊、Eval 結果及已知例外。Lean 版本不是展示文案，而是可被同一任務重複執行的正式資產。

再建立一張 Prompt Review Checklist：是否每條規則只出現一次、是否有未使用工具、範例是否修正實測缺口、背景是否動態載入、輸出是否重複、權限邊界是否一致。每次新增提示內容，先說明要修正哪個測試案例。

BASE原始可用版

保存作為回復與品質基準

LEAN精簡候選版

只保留經測試有價值的內容

EVIDENCE比較報告

Token、品質、失敗與例外

RULE新增內容需有理由

必須對應任務需求或實測缺口

BEFORE / AFTER

2600 Token 的 System Prompt，怎麼縮到 1100？

WASTEFUL

重複三次權限政策、列出 18 個永遠可見工具、放入 9 個相似範例，並要求多輪自我反思。

OPTIMIZED

權限合併成一段；工具按任務暴露；只保留 2 個修正實測錯誤的範例；把反思改成最終驗收。

WHY IT WORKS

前綴下降，工具路由更清楚；在固定 Eval Set 中品質持平後才採用。

FIELD ASSIGNMENT

替一份真實 Prompt 做三輪 Ablation

不要從空白重寫；選擇目前真的能完成任務的版本。

  1. 00–15

    分組與去重按目標、限制、工具、範例、風格與輸出標記。

  2. 15–30

    移除第一組刪除重複規則，跑固定 Eval。

  3. 30–45

    移除第二組縮小工具或條件式載入範例，再次重跑。

  4. 45–60

    產出比較表記錄 Token、成功、例外、採用與回復條件。

CHECK YOUR MODEL

先回答，再展開。

最短的 Prompt 就是最省 Token 的 Prompt 嗎？

不是。過度刪減可能降低成功率與增加重試；目標是通過品質門檻的最低總成本。

範例是不是都該刪掉？

不是。保留能鎖定產品格式或修正實測缺口的範例；無差異、重複性範例才先移除。

工具規則全部放 System Prompt 有何問題？

未使用工具的說明會永久進入前綴，也讓路由選擇變複雜；細節應靠近工具並按任務載入。

要求模型逐步思考能提高品質嗎？

不應假設。優先給目標、證據與成功條件；只有可稽核業務流程才固定外部步驟，並用 Eval 驗證。

如何避免精簡掉安全規則？

把安全與權限列為 Must-have，使用邊界案例回歸；精簡只採用在安全行為仍通過時。
