COURSE OUTLINE / CHAPTER 01

TRACE EVERY TOKEN

Agentic AI 的 Token 成本地圖

Agent 不只回答一次：它會帶著系統指令、歷史、工具定義與工具結果反覆呼叫模型。第一章先把這條看不見的帳單拆開，建立一張能指向真正浪費來源的成本地圖。

65–85 分鐘8 個完整段落實例＋模板＋作業品質優先

LEARNING OUTCOME

完成本章後，你能把一個 Agent 任務拆成回合與階段，辨認輸入、輸出、推理、快取與工具內容的成本，並用『總 Token × 呼叫次數 × 重送比例』找出前三個浪費熱點。

IMPORTANT BOUNDARY

本課程談的是工程上的資源效率，不承諾任何平台固定價格；費率、模型功能與計費欄位可能改變。實作以相對用量與每個成功任務成本為主，價格需回到你使用的平台確認。

01

TRACE THE LOOP

Token 會在每一次『看、想、做、再看』中累積

一般聊天常讓人只注意最後那段回答，但 Agent 會先讀目標、決定工具、接收工具結果、檢查狀態，必要時再呼叫下一個工具。每次模型呼叫都是一張新的小帳單，而前面固定指令、工具說明與部分歷史經常再次出現。

因此真正要優化的單位不是『某一則回答』，而是完整任務 Run。先畫出每個回合的輸入、模型輸出、工具呼叫、工具回傳與是否重試；同一段一萬 Token 的背景若被帶進八個回合，影響遠比最後多寫三百字更大。

INPUT系統與任務

規則、目標、背景、檔案與歷史

MODEL判斷下一步

產生回覆、推理或工具呼叫

TOOL取得外部結果

搜尋、資料庫、程式、檔案與瀏覽器

LOOP重新帶回上下文

結果加入歷史後再次呼叫，直到完成

圖解｜一個 Agent 任務不是一次回答 每多一個回合，不只多一段輸出，也可能再次攜帶固定前綴、工具定義與歷史。

02

READ THE USAGE

不要把 Input、Output、Reasoning 與 Cached Token 混成一個數字

輸入 Token 是模型本回合看見的內容；輸出 Token 是回覆、工具參數或最終答案；推理 Token 代表模型內部為任務投入的推理資源；快取 Token 則是重複前綴被系統辨識後的使用量細節。不同供應商呈現方式不同，但概念上都需要分開看。

工具本身的 API 或運算費用通常不是模型 Token，工具回傳一旦放入模型上下文卻會變成輸入。多 Agent 還會建立多份獨立上下文。分析報表至少保留模型、階段、輸入、輸出、快取、推理、呼叫數與工具輸出大小，否則只能看到總額，無法知道該改哪裡。

INPUT模型看見多少

固定提示、歷史、檔案、工具 Schema 與結果

OUTPUT模型說了多少

文字、JSON、工具參數與最終答案

REASONING模型想了多少

依任務難度與設定投入的內部工作

CACHED有多少可重用

重複前綴是否被命中，仍要看平台用量欄位

圖解｜先分清楚五種 Token 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

最常見誤判

只要求『回答短一點』通常只影響最後輸出；如果最大成本來自重送歷史或巨大工具結果，總帳單幾乎不會明顯下降。

03

MODEL THE TOTAL

把每回合的內容與呼叫數乘起來

可以先用一個平台無關的近似式：總模型用量＝所有回合的輸入＋所有回合的輸出＋可計費推理；完整任務成本還要加上工具、搜尋、儲存與失敗重跑。快取會改變相同輸入的實際價格，但不代表內容可以無限增長。

更實用的診斷式是：浪費影響≈內容大小×被重送的回合數×不相關比例。五百 Token 的固定規則重送十次是五千；兩萬 Token 的工具日誌若九成無關，即使只發一次也有一萬八千 Token 的削減空間。先估數量級，不必一開始追求小數點精度。

浪費影響 ≈ 內容大小 × 重送次數 × 無關比例
成功任務成本 = 所有嘗試的總成本 ÷ 成功任務數
SIZE內容大小

這段提示、歷史或結果本身有多大

REPEAT重送次數

在多少回合或多少 Agent 中再次出現

NOISE無關比例

模型真的需要其中多少內容

IMPACT優先順序

先改 SIZE × REPEAT × NOISE 最大者

圖解｜建立完整成本公式 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

04

FIND THE PREFIX

系統提示、技能與工具定義會陪著 Agent 走很久

系統規則常被視為免費背景，但它們通常位於每次模型呼叫的開頭。若把所有專案規範、所有工具手冊與大量範例永久塞進前綴，一個很小的任務也要反覆閱讀整套操作手冊。前綴越長、回合越多，乘數效應越明顯。

先把規則分成全域必須、任務類型需要、特定工具需要與本回合動態資訊。全域只保留跨任務都成立的硬限制；工具細節放入工具描述；長篇參考資料改成需要時檢索。之後再談快取，因為快取只能讓重複便宜，不能修正不相關內容造成的判斷干擾。

GLOBAL跨任務硬規則

安全、權限與核心輸出契約

ROUTE任務類型規則

只有進入對應流程才載入

TOOL工具自己的說明

用途、輸入、輸出、錯誤與副作用

DYNAMIC本回合資料

使用者目標、檔案片段與當前狀態

圖解｜固定前綴是沉默的乘數 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

05

WATCH CONTEXT GROWTH

每一個新工具結果都可能成為下一回合的舊歷史

假設回合一載入八千 Token，工具回傳四千；回合二若把全部歷史再送一次，輸入可能已接近一萬二千。回合二再增加六千行日誌，回合三便可能再次攜帶前兩輪內容。這種累積讓長任務後半段突然變慢、變貴，也更容易讓模型抓錯重點。

上下文管理要像程式的記憶體管理：保留仍影響決策的目標、限制、證據與未完成事項；已完成的探索、重複日誌與被淘汰方案則轉成短摘要或外部 Artifact。每個 Checkpoint 記錄『現在狀態』而不是逐字保存『怎麼走到這裡』。

TURN 1目標＋固定前綴

初始成本可控

TURN 2加上工具結果

舊內容開始被重送

TURN 3加上錯誤與重試

歷史與日誌快速膨脹

CHECKPOINT留下狀態摘要

決策、證據、未完成與下一步

圖解｜歷史會複利成長 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

06

COUNT EVERY CONTEXT

平行化節省的是時間，不會自動節省 Token

協調者把相同需求與參考資料交給四個子 Agent，就可能複製四份輸入；每個 Agent 各自搜尋、解釋與回報，最後協調者還要再讀一次所有結果。若工作不能乾淨切開，多 Agent 甚至會同時研究相同問題。

多 Agent 的合理收益是降低牆鐘時間、增加獨立檢查或讓不同專長並行。要討論 Token，必須把協調提示、每個子任務上下文、各自工具輸出、交接結果與最終統整全部加總。只有當分工能減少重複探索、讓每個 Agent 看到更小範圍或明顯降低失敗率，才可能在總成本上划算。

COORDINATOR拆分與統整

本身也有上下文與輸出成本

AGENT A獨立子上下文

只應拿到 A 真正需要的資料

AGENT B獨立子上下文

避免和 A 重複研究

MERGE精簡交接

結論、證據、風險與未解問題

圖解｜多 Agent 會複製上下文 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

07

MAP YOUR OWN RUN

不用精密圖表，也能定位前三個浪費熱點

挑一個近期真實任務，把每一次模型呼叫列成一列：階段、目的、輸入、輸出、工具回傳大小、是否重試、是否成功。再把輸入粗分成固定前綴、任務資料、歷史、工具定義與工具結果。這張表會立刻揭露成本是被哪一類內容拉高。

接著為每一類標記『必要／可以摘要／可以外置／完全不需要』。先挑最大的三格做實驗，不要同時改所有東西；一次移除或縮小一組，重新執行相同任務並比較品質。這是全課程反覆使用的基本節奏：量測、改一件事、重跑、保留或回復。

OBSERVE逐回合記錄

呼叫、輸入、輸出、工具、重試與結果

CLASSIFY按來源拆開

前綴、任務、歷史、工具 Schema、工具結果

RANK找前三大

依大小、重送與無關比例排序

CHANGE一次改一組

以同一組任務重新驗證

08

DELIVER THE COST MAP

你應該能指出『哪裡浪費』，而不是只說『Token 很多』

本章完成品是一張任務成本地圖：至少包含五個回合或完整流程、每回合內容分類、工具結果大小、重試原因與最後是否成功。再列出前三個浪費熱點，以及每個熱點預計用哪一章的方法處理。

若你還拿不到精確 Usage，也可以先用字元數、檔案大小、行數與回合數作代理指標。重點是建立可重複比較的基準，而不是得到看似精密但無法行動的數字。第二章會把這張圖轉成正式 Scorecard。

DELIVERABLE 1一張回合表

至少列出目的、內容來源與結果

DELIVERABLE 2三個浪費熱點

大小、重送與無關比例都有說明

DELIVERABLE 3一項先做實驗

只改一組內容，保留比較基準

DELIVERABLE 4品質不可退步

定義什麼叫任務仍然成功

圖解｜第一章完成標準 把每一步的輸入、判斷與輸出分開，才看得見真正可以縮減的地方。

BEFORE / AFTER

同一個任務，浪費可能藏在完全不同的位置

WASTEFUL

只看最後答案 700 Token，便要求模型再短 30%。

OPTIMIZED

追蹤到 6 次呼叫共重送 48,000 Token，先將 20,000 Token 日誌在工具端聚合成 1,200 Token。

WHY IT WORKS

輸出長度幾乎不變，但總輸入大幅下降；優化仍保留完整結論與證據。

FIELD ASSIGNMENT

用 40 分鐘畫出一個真實任務

選擇你最近用 Agent 做過的任務；沒有 Usage 也能先用字數與行數估算。

  1. 00–10

    列出所有回合記錄每次模型與工具呼叫的目的、結果和是否重試。

  2. 10–20

    拆分輸入來源標記固定前綴、任務、歷史、工具定義與工具結果。

  3. 20–30

    算浪費影響以大小×重送×無關比例找出最大的三格。

  4. 30–40

    定義第一個實驗只選一項縮減，寫下成功條件與回復方式。

CHECK YOUR MODEL

先回答，再展開。

為什麼最終回答很短，任務仍可能很貴？

Agent 可能在多個回合重送長前綴、歷史與工具結果；最終輸出只佔總用量的一小部分。

工具 API 沒有 Token，為什麼仍要管工具輸出？

工具結果被放回模型上下文後會成為輸入 Token，而且常在後續回合被再次攜帶。

快取命中後，長提示就不需要精簡嗎？

仍需要。快取只改變部分重複輸入的成本與延遲，不會消除不相關內容對判斷與上下文窗口的干擾。

多 Agent 一定比單 Agent 貴嗎？

不一定；若能讓每個 Agent 看到更小範圍、降低重複探索或失敗率，總成本可能合理，但必須加總所有上下文。

沒有精確 Token Usage 還能開始嗎？

可以。先用字數、檔案大小、行數、回合與重試作代理指標，建立一致基準後再換成精確資料。
