Advanced Data Structures

Count-Min Sketch

用多列計數器近似高流量事件頻率

進階32 分鐘PYTHON 3

WHY THIS MATTERS

實作 Count-Min Sketch，理解只高估不低估、誤差來源與串流選型。

LEARNING GOALS

  • 描述 width 與 depth 的作用
  • 實作 update 與 estimate
  • 理解高估保證與限制
01

固定空間摘要巨大鍵空間

Count-Min Sketch（CMS）用 depth 列、每列 width 個計數器摘要事件頻率；每次事件在每列各增加一個雜湊位置，查詢取各列計數最小值。它不保存所有鍵，適合網路流量、點擊與日誌串流的近似計數。

  • 空間 O(depth × width)
  • 更新與查詢 O(depth)
  • 不同列使用不同雜湊
  • 空間不隨不同鍵總數直接成長
02

最小值降低碰撞高估

每個計數器包含目標和碰撞鍵的次數，因此不會低於真實頻率，只可能高估；取多列最小值可避開部分碰撞較嚴重的列。width 主要控制誤差幅度，depth 主要降低超出誤差保證的機率。

  • 標準正增量下 estimate ≥ true count
  • 碰撞只會增加估計
  • 更大 width 降低加性誤差
  • 更大 depth 提高信賴度
03

近似頻率不是完整排名答案

CMS 適合點查詢某鍵的近似次數，但它未保存鍵本身，不能單獨列出所有 Top K；通常要搭配候選集合或 Heap。需要精確帳務、負增量或刪除時，標準只增 CMS 的保證不再直接適用，應選精確 dict 或其他 Sketch。

  • 適合允許小幅高估的監控
  • 不能單獨枚舉鍵
  • 精確計數使用 dict
  • 可合併相同尺寸與雜湊設定的 Sketch

RECAP

這堂課要帶走的事

  1. 01CMS 以固定二維計數器近似大量鍵頻率
  2. 02標準正增量下估計只高估，取多列最小值降低碰撞影響
  3. 03它適合串流點查詢，但不能獨自還原鍵或精確 Top K

CHECK YOURSELF

先想一想，再看答案

為何 estimate 取最小值而不是平均值？

每列碰撞只會增加計數；取最小值選擇污染最少的一列，同時維持不低估性。

CMS 能否列出所有出現次數最高的鍵？

不能單獨做到，因為它只保存計數器不保存鍵；需搭配候選鍵結構。

PRACTICE

延伸練習

  1. 建立小 width 的 CMS，加入多個鍵並比較 estimate 與 dict 真實值。
  2. 設計 CMS 加候選 Heap 的熱門事件流程，說明兩者各保存什麼。
